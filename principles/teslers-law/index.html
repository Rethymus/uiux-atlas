Tesler 定律 Tesler's Law

复杂度守恒定律 · Conservation of Complexity

任何系统都有不可消除的复杂度——不是由系统承担,就是由用户承担。设计的目标是把固有复杂度从用户身上挪到系统里。

结构与 DOM

演示是同一张寄件表单的两种承担方式:字段由 fields 参数决定(3–8 项),模式由 mode 切换:

<div class="tl-row">
  <label for="tl-recipient">收件人</label>
  <button class="tl-fill">填写 fill</button>       <!-- manual:用户点一次填一项 -->
</div>
<div class="tl-row">
  <label>地址</label>
  <span class="tl-lock">系统代填 by system</span>   <!-- assisted:预填并锁定 -->
</div>

关键点:

  • manual 模式:全部字段给「填写」按钮,每点一次计一次用户操作;「演示填写」按 300ms/项的节奏自动点,模拟真实填写负担;
  • assisted 模式:前 fields−2 项显示「系统代填」并给出示例值(收件人/电话/地址等来自账户与历史订单的语境),带「修改」出口可解锁——复杂度转移不等于剥夺控制;
  • 底部复杂度分配条实时显示「用户 n 项 / 系统 k 项」——总宽度不变,变的只是分界线位置,这就是「守恒」。

样式与参数

// mode / fields 是 JS 型参数:demo 订阅 store 驱动
const sysCount = assisted ? Math.max(0, fields - 2) : 0;
const allReady = active.every((f) => filled[f.key]);
  • fields 默认 6、mode 默认 manual:先体验 6 项全填的负担,再切 assisted 看 4 项被系统接管;
  • 「演示填写」300ms/项是 demo 模拟节奏,不是定律数值;它的作用是把「用户操作次数」变成可感知的时间;
  • 复杂度条紫=用户承担、绿=系统承担:两种颜色+文字图例双通道,不只靠色(呼应 SC 1.4.1)。

动效与交互

  • 复杂度条的紫/绿两段用 0.25s width 过渡平滑移动;prefers-reduced-motion 下取消过渡;
  • 每次点击「填写」操作计数 +1;面板实时显示已就绪 n/fields;
  • 「修改」解锁预填项后,该项从「系统承担」回到「用户承担」——分配条立刻反应,这正是定律的另一面:转移是有代价与风险的(预填错了比空白更危险);
  • 提交按钮在全部就绪前置灰——可用性状态也是状态反馈的一部分。

真实产品案例

  • 电商收货地址预填:收件人/电话/地址从账户与历史订单带出,用户只补增量信息——「工程师多花一周,好过百万用户各多花一分钟」在收银台的经典兑现(07§26 指导的泛化,调研未点名单一产品);
  • 快递/外卖的下单默认项:时段、包装、发票等以智能默认值出现,90% 用户直接下一步——把「理解全部选项」的复杂度收归系统(07§26「把指引放进使用上下文」);
  • Cloudinary/托管服务的「自动优化」(编辑性泛例):「上传即自动压缩/转码/CDN 分发」把图像工程参数的复杂度整体接管,用户只给一张原图——复杂度没有消失,只是全部由系统承担。

参数敏感度

参数调大会…调小会…
fields表单变长,manual 的点击次数线性上涨,assisted 的「系统承担」占比也变大(fields−2)3 项时两种模式差距缩小,实验张力减弱
modeassisted:预填锁定 + 2 项可编辑,操作次数骤降;记得点「修改」体验夺回控制manual:基线对照——全紫的分配条就是「复杂度全在用户」的样子

经验结论:复杂度守恒的落点是分配决策,不是消灭决策——每一次「要不要让系统代办」都要同时回答「预填错了怎么办」;没有回滚出口的自动化不是省复杂度,是换一种更贵的复杂度。

适用场景 3
  • 表单预填:从账户/历史订单带出已知信息,只问增量
  • 智能默认值:90% 用户会选的选项直接设为默认
  • 把「专业术语 + 组装配置」封装成一个系统判断,用户只给意图
何时不要用 2
  • 为「理想理性用户」设计——假定用户愿意理解全部参数(07§26 告诫)
  • 把复杂度「藏」成黑盒:用户既没省事,也失去了纠错出口
无障碍

系统代办不能替用户做不可见决定:预填字段必须可辨识、可修改(锁定的只读项要有文本说明「已从历史订单带出」);表单语义完整(label 关联、fieldset 分组),复杂度转移不以牺牲可理解为代价(呼应 SC 1.3.1/3.3.1)。

浏览器支持

纯 DOM 交互,全现代浏览器可用。

兼容回退

复杂度守恒没有 CSS 回退,工程出口是「转移而非消灭」:智能默认值、上下文预填、向导分步、tooltip 内嵌帮助(07§26)。转移的代价记在系统侧——预填错了比空白更危险,assisted 模式必须保留「改掉默认值」的出口。

来源 1

起源由 Larry Tesler(Xerox PARC / Apple)提出,又称复杂度守恒定律:复杂度守恒,只能转移,不能消灭(Jon Yablonski,Laws of UX;调研 07§26)。调研 07§26 的指导:设计与开发阶段尽量把固有复杂度从用户身上挪走——「工程师多花一周,好过百万用户各多花一分钟」;不要为「理想理性用户」设计;把指引放进使用上下文。

  1. 条目 生成式 UI

    搭配:工具调用是复杂度守恒的当代样本:模型代跑 get_weather、宿主只渲染结果卡——复杂度没有消失,只是转移到系统侧,渲染权仍在白名单手里。

  2. 条目 Doherty 阈值

    搭配:系统代填把用户操作换成等待确认——assisted 预填需要乐观更新那样的两阶段反馈,而「修改」出口对应失败回滚:转移复杂度要连反馈策略一起设计。

  3. 条目 Hick 定律

    反向自「Hick 定律」的精选:搭配关系,原句「Hick 的「决策压到最少」在 Tesler 这里有系统侧解法:智能默认值出现后 90% 用户直接下一步——减的不是选项,是承担复杂度的一方。」
