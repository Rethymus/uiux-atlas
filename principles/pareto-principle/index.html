帕累托法则 Pareto Principle

80/20 法则 · 80-20 Rule · 二八法则

约 80% 的效果来自约 20% 的原因——「约」字是法则的一部分。识别带来最大收益的少数关键区域,把精力集中投给它;但别机械套用。

社区流派 ★★★
实例演示 官方默认
参数
几何▾
skew1.9

JS 型参数:分布偏斜度(demo 教学模型 share ∝ 1/rank^skew,归一化为占比)。默认 1.9 时 10 项功能中前 2 项承载约 78.4%(demo 实时实算显示)——复现「约 80/20」形态。定律本身只给「约 80/20」的定性描述,不规定任何分布参数。

budget2项
项

JS 型参数:「重点打磨」的工程预算——demo 高亮收益排序前 budget 项,并给出覆盖占比与剩余项合计。默认 2 对应「20% 关键区域」;从 2 调到 4,覆盖从约 78% 升到约 86%,增益骤减——收益递减曲线即「集中投资少数」的量化理由。

关键点:

  • 10 项功能按收益排序横轴排列,占比由 share ∝ 1/rank^skew 实时归一化实算——所有百分比都来自当前参数的计算结果,没有一个数字写死 80;
  • 结论双通道:柱状图之外,「前 2 项承载 X% / 80% 线:前 k 项 / 预算覆盖 Y%」以文本常驻(aria-live 同步),面板逐项列出前 5 名名称与占比;
  • 预算高亮是双通道的:柱体变色 + 逐项「预算内」文字标签,不靠颜色单独传达。

样式与参数

// skew / budget 是 JS 型参数,订阅 store;占比实时计算
const raw = FEATURES.map((_, i) => Math.pow(i + 1, -skew));
const shares = raw.map((r) => (r / raw.reduce((a, b) => a + b, 0)) * 100);
const k80 = cum.findIndex((c) => c >= 80) + 1;   // 80% 线所在名次
  • skew 默认 1.9:此时 10 项中前 2 项承载 ≈78.4%(实时实算),复现「约 80/20」形态;该值是 demo 教学模型参数,定律本身只给「约 80/20」的定性描述(lawsofux 原文强调 roughly,非精确值);
  • budget 默认 2 项:对应「20% 关键区域」;调到 4 项覆盖约 86%——增益从 ~78%→~86% 明显放缓,收益递减曲线就是「集中投资少数」的量化理由;
  • 出处数值:帕累托观察「意大利约 80% 土地归 20% 人口」、UX 应用原句「将大部分精力集中于能为最多用户带来最大收益的领域」、误用警告「机械套用(如只顾减少点击次数)」——全部取自 12 补研 §14;
  • 80% 参考线画在右侧 0–100% 累计轴上,findIndex(c >= 80) 给出「达到 80% 所需前 k 项」。

动效与交互

  • 拖动 skew:柱体高度与累计曲线用 transition: y/height/d 0.3s ease 平滑重排(SVG 几何属性,不支持时退化为直接跳变,无兼容风险);
  • 拖动 budget:高亮柱集合即时切换,面板「预算内」标签同步;
  • prefers-reduced-motion: reduce 下两处过渡取消,数值即时更新;
  • SVG 带 role="img" 与动态 aria-label(含前 2 项占比、预算覆盖、80% 线名次),读屏可得不依赖视力的结论。

真实产品案例

  • 分析驱动的功能分层(泛例):埋点/漏斗找出使用率前 20% 的功能集中打磨,是 12 补研 §14 原句「将大部分精力集中于能为最多用户带来最大收益的领域」的直接落地;本 demo 的「按收益排序 + 预算」就是该流程的教学化;
  • 工具栏 / 主菜单分层惯例(泛例):高频动作常驻显性位置、低频能力收进「更多」——界面层的 80/20,与序位效应「关键动作放最左最右」(调研 07§29)互补:一个分「多少」,一个分「位置」;
  • 误用警戒(12 补研 §14):lawsofux 点名的机械套用——「只顾减少点击次数」一类机械代理目标,不是收益本身;80/20 是诊断透镜,不是裁剪长尾功能的手术刀。

参数敏感度

参数调大会…调小会…
skew3.0:分布更陡,前 2 项承载升到 ~93%——「头部集中」的极端形态,80% 线只需前 2 项1.5:分布变平,前 2 项承载降到 ~67%,80% 线退到前 4 项——平权世界里集中投资理由减弱
budget10 项:覆盖 100%,但「平均用力」;对照 2 项的 78% 可见增益多么不成比例2 项:恰好「20% 预算」,覆盖 ~78%——再往下不在滑块范围(min=2)

经验结论:先用数据找到头部 20%,把打磨预算集中投给它;80/20 是「roughly」的近似——用它排优先级,别用它做精确承诺,更别机械裁掉长尾里战略关键的少数功能(12 补研 §14)。

适用场景 3
  • 版本规划:识别使用率/收益前 20% 的功能,优先打磨、优化性能与可达性
  • 界面分层:高频动作常驻显性位置,低频能力收进「更多」
  • 性能与质量投入:先优化覆盖最多用户的头部路径,再处理长尾
何时不要用 3
  • 机械套用 80/20:lawsofux 点名的误用是「只顾减少点击次数」一类机械目标,不是收益本身
  • 把 80/20 当精确值汇报或写死在代码里——「roughly」是法则原文的一部分
  • 砍掉低用量但战略关键的长尾功能(合规、无障碍、企业客户必需项)
无障碍

柱状图信息必须双通道:SVG 之外,「前 2 项承载 X%」「80% 线:前 k 项达到」「预算覆盖 Y%·剩余合计 Z%」全部以文本呈现并随参数实时更新;预算高亮同时用颜色与「预算内」文字标注,不靠颜色单独区分;SVG 带 role=img 与动态 aria-label;prefers-reduced-motion 下柱体与曲线过渡取消,数值即时更新。

浏览器支持

演示用内联 SVG 绘制柱状图与累计曲线,全现代浏览器可用。

兼容回退

定律的工程出口:用分析数据(使用率/收益)给功能排序,预算向头部集中。可降级路径:拿不到埋点数据时,用上一迭代的高频功能清单或客服工单 Top N 作代理;没有排序依据时,至少保证头部路径(首页→核心任务)的手工打磨优先级。红线:80/20 是近似值,别机械裁掉长尾中的战略性少数功能——lawsofux 点名的误用正是「机械套用(如只顾减少点击次数)」。
