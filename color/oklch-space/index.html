OKLCH 色彩空间 OKLCH Color Space

oklch 色彩空间 · 感知均匀色彩空间 · Perceptually uniform color space

CSS 官方感知均匀色彩空间 oklch(L C H / A):数值变化即人眼感知变化——本条讲空间本身的四个分量与坐标语义。

L70%
%

感知亮度:0=黑、100=白,也可写作 0–1。L 轴与人眼感知线性一致——等步长的 L 变化看起来等亮(这是 oklch 与 HSL 的根本区别,HSL 的 L 与真实感知亮度不一致)。工作流参照值:Evil Martians 的 L=0.8(配黑字都清晰)、L≥87%(背景配黑字对比度恒达标)。默认 70 为条目快照(调研未载官方默认)。

C0.15

色度(chroma),0=无彩色灰。MDN:理论上无上限,但实践中不超过 0.5,且注意 100% = 0.4 而非 1。Evil Martians 实测:sRGB 色域的实际边界约 0.37(P3 屏略高)——越过即溢出色域,浏览器(Chrome/Safari)会直接裁剪 RGB 导致色相跑偏。默认 0.15 为条目快照,处于 sRGB 内的安全区。

H145deg
deg

色相角 0–360°。oklch 的色相刻度与 hsl/lch 都不重合:hsl 0°=红,CIELab 的红约 41°;Evil Martians 经验映射:红≈20°、黄≈90°、绿≈140°、蓝≈220°、紫≈320°。默认 145(绿)取自该映射。同一 L/C 下转动 H,感知亮度几乎不变。

alpha1

透明度,语法上以 / 分隔:oklch(L C H / A)。1=完全不透明,0=全透明;半透明时透出的背景会参与最终观感与对比度。默认 1(不透明)。

代码拆解

结构与 DOM

oklch() 是 CSS Color 4 收录的函数,本身没有任何 DOM 要求——它只是一个颜色值。把它用起来的最小结构是一个被它上色的元素,加上一条用于展示分量语义的读数:

<div class="swatch"><!-- 被 oklch() 上色的块 --></div>
<span class="readout">oklch(70% 0.15 145)</span>
  • 颜色值与元素解耦:可以出现在 color、background-color、border-color、fill、shadow 等一切接 <color> 的属性上;
  • 半透明度写在斜杠后:oklch(70% 0.15 145 / 0.5),元素底下透出什么,最终观感就是什么;alpha 同样接受百分比写法,与 color-mix(in oklab, …) 组合可衍生半透明色(Tailwind v4 的透明度姿势,调研 06§一4);
  • 缺省分量也是合法语法:oklch(none 0 none) 即 W3C 用作去色动画的示例(CSS Color 4 §4.4,调研 06§一1);
  • demo 用 JS 实现同样的换算(Ottosson 矩阵),便于把每一步数值摆出来核对。

样式与参数

四个分量各有明确语义:L 感知亮度(0 黑 → 100 白)、C 色度(0 = 灰)、H 色相角、alpha 透明度:

.swatch {
  /* 基础兜底在前,oklch 覆写在后 */
  background-color: rgb(91 182 97);
  background-color: oklch(70% 0.15 145);
  color: oklch(0.15 0.03 145);
}
@supports (color: oklch(70% 0.15 145)) {
  .swatch { border-color: oklch(70% 0.15 145 / 0.4); } /* alpha 用 / 分隔 */
}
@media (color-gamut: p3) {
  .swatch { background-color: oklch(70% 0.37 145); }  /* P3 上放开色度 */
}

数值出处(调研 06§一1/§二2):

  • L 取 0–1 或 0%–100%,0=黑、1=白(MDN);C 实用上限约 0.5,且 100% = 0.4 而非 1(MDN);
  • H 0–360°,但刻度与 hsl/lch 均不同:hsl 0°=红,CIELab 红约 41°;Evil Martians 映射:红≈20°、黄≈90°、绿≈140°、蓝≈220°、紫≈320°(本条默认 145 即「绿」);
  • C 的 sRGB 实测边界 ≈ 0.37(P3 屏略高);Chrome/Safari 现状是直接裁剪 RGB 而非按规范降 chroma,色相会肉眼可见地跑偏,建议手写 P3 覆盖规则;
  • 百分比记法在 C 上尤其易踩坑:100% 只等于 0.4,一句 oklch(70% 100% 145) 就已越过 sRGB 边界——日常建议用小数记法;
  • Baseline「广泛可用」= 2023 年 5 月。

动效与交互

  • 改任一分量,颜色与读数即时重算。感知均匀性最直观的证明:同 C/H、L 等步 +10 的阶梯看起来是等亮度间隔——demo 用 JS 逐档换算 sRGB 后平铺 10 档;
  • 感知均匀的交互收益:hover 提亮可写成相对颜色 oklch(from var(--c) calc(l + 0.1) c h)(CSS Color 5;calc 只能加减数字)——同一 Δl 对任何色相都是等感知步(调研 06§二2);
  • 渐变同理:显式声明 linear-gradient(in oklch, …) 指定插值空间,长距色相过渡不再出默认 sRGB 插值的脏灰带(CSS Color 4 §13,调研 06§一4);
  • 色块过渡只动 background-color(0.18s),prefers-reduced-motion 时取消过渡直接跳变;
  • 不做位移动画:颜色空间的演示里任何 transform 都只是干扰;
  • 溢出 sRGB(任一通道换算后越出 [0,1])时如实亮警示条,并按浏览器现状裁剪展示——这也是真实网页在非 P3 屏上的遭遇。

参数敏感度

参数调大会…调小会…
L变亮:对黑字对比度下降、对白字上升;≥87% 的背景配黑字对比度恒达标(Evil Martians)变暗:对黑字对比度上升;低于 ~50% 白字才开始可行;0/100 即黑/白,C/H 失去意义
C更鲜艳;超过 ≈0.37 溢出 sRGB,被裁剪后色相跑偏(P3 屏可放开)趋向灰;C=0 时颜色完全由 L 决定,黑白两端对比度也最极端
H沿色环转动(145=绿、220=蓝):同一 L/C 下感知亮度几乎不变反向转环;高 C 区域转动可能触发色域裁剪
alpha叠透出更多背景,元素与背景互相渗透,对比度按合成结果变化趋向实色;0 时完全不可见

要点:先用 L 定「多重」,再用 C 定「多鲜艳」,H 只决定「什么色」;本条讲空间本身——固定 L 只调 C/H 的选色工作流与对比度工程,见姊妹条目 oklch-workflow。

适用场景 4
  • 任何需要『数值等步 = 感知等步』的场合:色阶推导、渐变插值、hover 提亮
  • 带透明度的主题色:oklch(L C H / A) 一条声明同时表达颜色与 alpha
  • 广色域显示:P3 屏上放开 C 到 0.37 以上获得更鲜艳的品牌色
  • 与 light-dark()/color-mix 组合:oklch 语义分量让暗色主题改 L/C 而不改色相
何时不要用 3
  • 把 hsl 的色相角直接搬进 oklch——两套角度不重合,红在 oklch 里约 20° 而非 0°
  • 把 C 当 0–100 的百分数用:100% 只等于 0.4,而 sRGB 实际边界约 0.37
  • 高 C 值直接上线——Chrome/Safari 现状是裁剪 RGB 而非降色度,色相会肉眼可见地偏移
无障碍

L 是感知亮度,是对比度的第一决定因素:WCAG 2.1 正文 AA≥4.5:1、AAA≥7:1(阈值不得四舍五入)。半透明色(alpha<1)叠在不可控背景上时,对比度按『合成后的最亮/最暗状态』核对,不能只按原色计算;Evil Martians 明示『仅靠 OKLCH 不保证可访问性,还需 APCA/WCAG 校验』。

浏览器支持

oklch() 自 2023 年 5 月起为主流浏览器广泛可用(CSS Color Module Level 4,Baseline);相对颜色语法 oklch(from …) 属 CSS Color 5,支持较新。demo 的上色与换算是纯 JS 数学(Ottosson 矩阵 + sRGB gamma),不依赖浏览器 oklch 支持。 · 2023

兼容回退

不支持 oklch() 的浏览器:先写 rgb()/hex 基础值,再用 @supports (color: oklch(0.7 0.15 145)) 包一层 oklch() 覆写;构建期可用 oklch.com 等工具把值换算成 sRGB 兜底。demo 直接以 JS 换算出的 rgb() 上色,天然兼容老引擎。
