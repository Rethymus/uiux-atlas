Font Loading Strategy

font-display · FOUT · FOIT · 字体加载 · block/swap/fallback/optional

@font-face's font-display decides how text renders while fonts load: five values map to block/swap period lengths — the web.dev table: fallback 100ms/3s, optional 100ms/no swap.

Code breakdown

Structure & DOM

font-display lives inside the @font-face rule — it is not a normal CSS property — governing how text renders while the font file loads:

<link rel="preload" href="/fonts/brand.woff2" as="font" type="font/woff2" crossorigin />
@font-face {
  font-family: "Brand";
  src: url("/fonts/brand.woff2") format("woff2");
  font-display: swap; /* one of auto | block | swap | fallback | optional */
}

body { font-family: "Brand", Georgia, serif; } /* metrically close fallback */

Key points:

  • Three periods (MDN): block (font not ready, text invisible) → swap (font not ready, fallback visible) → failure (treated as failed);
  • The fallback in the font-family stack is not decoration — it is exactly what the swap period shows, and its metrics decide layout shift;
  • Self-host first (web.dev practice); preload discovers the font earlier but competes with other critical resources.

Where the numbers come from: MDN font-display (five-value semantics) + web.dev font-best-practices (the numbers table), both verified from source (research 05 §21); auto’s concrete periods are not published uniformly across browsers — MDN’s “browser-defined” wording is the source of truth. The demo takes the upper bound for block (3s) and simulates auto as 100ms labeled “browser-defined”.

Motion & Interaction

The demo simulates a full load with a state machine equivalent to the numbers table:

  • “Reload” runs one timeline pass (0–3.5s) per current params: block segment (text invisible/placeholder) → swap segment (fallback Georgia) → the arrival point (switch to the demo webfont look) or failure;
  • Dragging the simulated-latency slider moves the font’s arrival time: swap waits forever; fallback gives up after 3s; optional gives up at 100ms (no swap this page);
  • Under prefers-reduced-motion: reduce the timeline doesn’t sweep — the state machine advances once to the final outcome for those params;
  • Phase transitions are implemented directly from the numbers table, not decorative animation — every invisible/swap moment you see is a row of that table.

Real-world examples

  • The Google Fonts CSS API: its served CSS carries font-display: swap by default (a stable, long-standing behavior) — plug in and you get “fallback visible immediately, swap when ready,” the largest-scale distribution of the FOUT strategy.
  • Next.js next/font: self-hosts fonts at build time, generates the @font-face with font-display automatically, and aligns fallback metrics (size-adjust et al.) — the official goal is eliminating swap-period layout shift.
  • Vercel’s website (Geist): research 05 §25 verified Geist ships as an npm package (npm i geist) loaded on demand — self-hosting plus framework-injected @font-face is the standard loading path for such engineering font packages.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
display → blockthe longest block period, 2–3s: slow networks leave users staring at blanks — the worst FOIT cost— (it is the longest-block tier)
display → swapfallback shows at 0ms; the font lands no matter how slow, with a possible shift at swap time—
display → fallback / optionalshorter swap periods lock the fallback in sooner on slow networks; optional has none at alla 100ms block is imperceptible; fast networks still swap normally
loadDelaypast the swap cap: fallback/optional keep the fallback forever while swap/block eventually land the fontunder 100ms all tiers converge — fast networks hide strategy differences

Takeaway: choosing a strategy is choosing what users see on the worst network — swap for body (content first), fallback/optional for brand faces (layout stability first).

When to use 4
  • Body fonts: swap or auto — FOUT is acceptable and the font always lands
  • Non-critical display faces (decorative headings, icon fonts): optional — slow network keeps the fallback forever, zero layout shift
  • Brand-critical but skippable heading faces: fallback — swap only if arrived within 100ms+3s, else the fallback stays
  • Paired with prefers-reduced-data for a save-data degradation (standard set, no implementation yet, research 11 §3)
When not to use 4
  • block for body text — 2–3s of invisible text (FOIT) hurts reading and SEO alike
  • optional on a must-show brand face — on slow networks it never swaps in
  • Declaring font-display but ignoring fallback metrics — the swap-time layout shift shows up as CLS
  • Mixing display strategies within one family without distinguishing scenarios
Accessibility

Block periods (2–3s for block, undefined for auto) mean text invisible to everyone — screen readers may still reach the DOM, but magnifier/high-contrast users see blank space. Fallback-vs-webfont width differences reflow text during swap; metrically compatible fallbacks (size-adjust/ascent-override etc.) remove that. optional's never-swap stance is the safest for readability, but the brand glyph can't be relied on.

Browser support

font-display: Baseline Widely available (since 2020-01, MDN, research 05 §21); Chrome/Edge, Firefox and Safari all support the five values. The FontFace API's display descriptor offers equivalent runtime capability (the demo uses a state machine, avoiding per-version API differences).

Fallback

Ancient browsers without font-display fall back to near-default (auto/block-like) behavior with text always visible — nothing to fix. The real fallback lives outside the font: a metrically compatible system font in the stack minimizes FOUT/swap layout shift, plus <link rel="preload"> (mind that it competes with other resources).
