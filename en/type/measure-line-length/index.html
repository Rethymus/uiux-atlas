Measure & Line Length

measure · line length · 行长 · 栏宽 · 65ch

Cap body copy with the ch unit: keep average line length at 45–90 characters (incl. spaces) — too long strains vertical tracking, too short chops the rhythm.

ch

Max body-column width in ch units. The verified readable band is 45–90 characters on average (Butterick); the default 65ch sits mid-band and is a community convention (unverified). Note that ch is font-dependent: the same ch count has different physical widths in different typefaces.

fontSize16px
px

Body font size. ch is relative — a larger font size widens the same ch count, so character count per line is governed by measure alone while physical width depends on both. Default 16px is the browser's base body size.

Motion▾
alignleft

The text-align value. Left alignment keeps natural word spaces; justification distributes line-length differences into the spaces — a narrow justified column invites 'rivers'. Extreme measures amplify both alignment's flaws.

Code breakdown

Structure & DOM

Measure needs no new structure — it is just a max-width cap on the body-column container, declared in ch units (the width of the “0” glyph) so character count becomes a directly writable quantity:

<article class="prose">
  <h1>Headings are not capped</h1>
  <p>Body paragraphs are the constrained element…</p>
</article>
.prose p {
  max-width: min(100%, calc(var(--measure-width) * 1ch)); /* 65ch default */
  font-size: var(--measure-font);                          /* ch scales with size */
}

Key points:

  • The constraint applies to body paragraphs, not the page container — headings, nav and footers have their own width strategies;
  • The min(100%, …) wrapper lets narrow screens defer to the container without horizontal scrolling;
  • ch is a relative unit: a larger font size widens the same ch count — character measure is governed by measure alone; physical width depends on font size and typeface.

Styling & Parameters

Three parameters, all injected through --measure-* variables:

.prose p {
  max-width: min(100%, calc(var(--measure-width) * 1ch)); /* dimension, unit ch */
  font-size: var(--measure-font);                          /* dimension, unit px */
  text-align: var(--measure-align);                        /* left | justify */
}

Where the numbers come from:

  • 45–90 characters (incl. spaces): the verified recommendation from Butterick’s Practical Typography, about 2–3 alphabets; longer lines strain vertical tracking (research 05 §19);
  • 65ch default: a community convention (unverified) sitting mid-band, convenient for demonstrating both directions;
  • The traditional “45–75 characters” saying differs from Butterick’s 45–90; this entry follows the verified source, 45–90 (research 05 §19 note).

Motion & Interaction

Measure is a purely static constraint with no motion; the only “moving” part in the demo is live measurement:

  • The demo splits the sample text into per-character spans, groups them by offsetTop to count each line’s characters, and derives longest / average line readings with a needle on a 45–90 band;
  • Changing measure / fontSize / align re-runs the measurement immediately (a ResizeObserver covers window resizes);
  • The verdict copy applies to Latin text only — no verified per-character guidance for CJK lines exists in this research, so the Chinese sample shows wrapping behavior without a pass/fail verdict.

Real-world examples

  • Wikipedia (Vector 2022 skin): adds a maximum width to the article content on wide screens so long lines no longer stretch across the viewport — measure control landing at global-website scale.
  • Long-form platforms like Medium / Substack: article pages use a single narrow column clearly narrower than the available page width, paired with generous line-height — the standard shape of commercial “narrow column, long read” products.
  • E-book readers such as Kindle: text reflows to the device width while keeping the measure readable — content reflows to the column, and the measure stays controlled.

Parameter Sensitivity

Working ranges: body columns 45–90 characters; the demo default of 65ch is a community convention (unverified). Decide measure first, then type size — doing it backwards makes “how wide is 65ch” drift with the typeface.

When to use 4
  • Long-form body columns (articles, docs, blogs) — measure is the primary readability constraint
  • Paired with fluid type: clamp() font-size plus a ch cap so narrow screens narrow automatically
  • Width caps for multi-column layouts and text blocks inside cards
  • As a design token: declare --measure: 65ch once, reference everywhere
When not to use 4
  • Treating the whole page container as body copy — nav/footer aren't body text and don't need the cap
  • No cap on ultrawide screens, letting lines stretch past 120 characters
  • Force-capping naturally wide content (tables, code blocks) at 65ch — they have their own scroll/collapse strategies
  • Pixel widths only — the real character measure silently drifts when typeface or size changes
Accessibility

Overlong lines make vertical tracking error-prone for low-vision and dyslexic readers; a ch cap on body columns is a common way to satisfy WCAG SC 1.4.10 Reflow (no two-dimensional scrolling at 400% zoom) — community practice, SC text not checked verbatim in this research. WCAG 1.4.8 Visual Presentation (AAA) adds width limits, commonly cited as ≤80 characters — not verified verbatim; consult the SC text before citing.

Browser support

The ch unit is a CSS Values basic unit, widely available in all modern browsers (MDN); no compatibility risk here. Line measurement is done with per-character spans + offsetTop, zero dependencies.

Fallback

If ch is unavailable, fall back to an em/px max-width or a percentage — the essence of measure is a column-width cap; units are just the measuring stick. All modern browsers support ch, so no fallback is needed in practice.
