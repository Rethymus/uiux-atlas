text-wrap balance & pretty

text-wrap · balance · pretty · 平衡换行 · 防孤行

Two style values of the text-wrap shorthand: balance evens out line lengths (short text only — ≤6 lines in Chromium, ≤10 in Firefox), while pretty runs a slower, better algorithm to prevent orphans in long body copy.

Web Standard ★★
Live demo official default
Parameters
Motion▾
headingWrapbalance

The heading's text-wrap-style. Default balance — built for short text: evens line lengths and kills the 'one-word last line' embarrassment; mind the line cap (≤6 Chromium, ≤10 Firefox) beyond which it falls back to auto behavior. Official guidance: balance for headings and pull quotes.

bodyWrappretty

The body's text-wrap-style. Default pretty — the slower, better algorithm for long-form copy that minimizes orphans (last lines of one or two words); MDN notes a performance cost, 'use only when typography beats speed'. Firefox doesn't support pretty yet (BCD); unsupported browsers fall back to auto harmlessly.

Demo column width in ch — narrowing to 24–40ch is what forces multi-line headings and visible orphans; real sites' headings are naturally 1–3 lines and need no such cap. The 30ch default is a demo value, not a spec value.

Code breakdown

Structure & DOM

No special structure — text-wrap is a normal CSS property declared directly on heading and body elements:

<h2 class="headline">Headings wrap into a few even lines, no lonely last word</h2>
<p class="body">Long body paragraph…</p>
.headline { text-wrap: balance; } /* short text: even lines (≤6 lines in Chromium) */
.body     { text-wrap: pretty; }  /* long body: orphan prevention */

Key points:

  • text-wrap is a shorthand = text-wrap-mode (wrap/nowrap) + text-wrap-style (auto/balance/stable/pretty etc.) (MDN);
  • balance applies only to blocks with a limited number of lines — headings, buttons, pull quotes; on long body copy it no-ops past the line cap (≤6 lines in Chromium, ≤10 in Firefox);
  • pretty is the long-copy tool: a slower but better algorithm whose goal is minimizing orphans.

Styling & Parameters

Three parameters injected through --tw-* variables:

.demo h2 { text-wrap: var(--tw-heading); max-width: calc(var(--tw-width) * 1ch); }
.demo p  { text-wrap: var(--tw-body);   max-width: calc(var(--tw-width) * 1ch); }

Where the numbers come from (research 11 §2, verified from MDN/BCD):

  • Per-value support: balance = Chrome/Edge 114, Firefox 121, Safari 17.5; pretty = Chrome/Edge 117, Safari 26 (announced at WWDC25: “even out the ragged edge… prevent short last lines”), Firefox unsupported;
  • The shorthand overall is Baseline widely available since 2024-03;
  • Line cap: balance applies to ≤6 lines in Chromium, ≤10 in Firefox (MDN text);
  • Official guidance: short text (headings, pull quotes) gets balance; long body gets pretty (with a performance cost — use only when typography beats speed); editable content gets stable.

Motion & Interaction

The wrapping strategy has no motion; the interaction is “narrow until the phenomenon appears”:

  • The demo splits the heading into per-character spans grouped by offsetTop, showing each line’s character count and last-line share live — under balance the lines converge; under auto the last line tends to a lone word;
  • Dragging width down (24–40ch) forces multi-line headings and orphans, contrasting balance / pretty / stable / auto;
  • Badges at the top use CSS.supports("text-wrap", "…") to report this browser’s actual support for balance and pretty — on Firefox you’ll see pretty honestly marked “unsupported (auto fallback)”;
  • Every change is an instant reflow with no animation; prefers-reduced-motion needs no handling.

Real-world examples

  • Tailwind CSS: since v3.4 the framework ships text-balance and text-pretty utilities mapping to text-wrap: balance/pretty — the wrapping strategy entered the default vocabulary of mainstream frameworks, one class name away in any new project.
  • The Chrome for Developers / web.dev tutorials: when Chrome 114 shipped balance, the official articles personally demonstrated the “balance for headings, pretty for body” pairing and codified “stable for editable content” — that pairing became the community default from then on.
  • Firefox and Safari’s catch-up cadence: Firefox 121 completed balance; Safari 26 finally added pretty (WebKit’s WWDC25 note framing it as orphan prevention) — all three engines converging on “balance for headings, pretty for body” shows the division of labor is now a cross-browser consensus.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
headingWrapbalance converges heading lines and de-orphans the last line; past 6 lines (Chromium) it no-ops to autoauto restores greedy breaking: fill the first line, orphan the last
bodyWrappretty redistributes breakpoints to avoid one-two-word last lines; measurable cost on long copyauto breaks fastest but one-word paragraph endings are common

Takeaway: balance and pretty are not rivals but a short-text/long-text division of labor — balance for headings, pretty for body, stable for editable content, and not one declaration more.

When to use 4
  • All headings (h1–h6) and pull quotes default to balance — one CSS line ends ragged headings
  • Long body copy and card summaries use pretty against orphans (where pretty is supported)
  • Multilingual headings: balance works across CJK/Latin/mixed without manual breaks
  • Buttons, nav items, tags: balance evens two-line wrapping of short labels
When not to use 4
  • balance on long body copy — beyond the line cap (≤6 in Chromium) it no-ops and wastes computation
  • balance/pretty on editable content (inputs, contenteditable) — official guidance is stable
  • Sprinkling pretty across huge list items as if free — MDN states it carries a performance cost
  • Using balance as a substitute for fluid type/column design — it evens lines, it can't fix a too-narrow container
Accessibility

balance/pretty are pure line-breaking strategies that never change the text itself — transparent to screen readers. Killing one-character heading last-lines and one-word body orphans helps dyslexic and low-vision readers keep vertical tracking (short last lines are where line-swap errors peak). balance does not change contrast or size — line readability still comes from line-height and font-size. stable's predictability for editable content is part of accessible editing too.

Browser support

The text-wrap shorthand overall is Baseline widely available since 2024-03 (BCD/MDN). Per value: balance = Chrome/Edge 114, Firefox 121, Safari 17.5; pretty = Chrome/Edge 117, Safari 26 (announced at WWDC25), Firefox unsupported (BCD @main, research 11 §2). Unsupported browsers fall back to auto — pure enhancement.

Fallback

Graceful degradation means doing nothing: unsupported browsers wrap with auto and the page is perfectly fine; no @supports fallback block needed. For layered enhancement, wrap overrides in @supports (text-wrap: balance); Firefox's missing pretty is the norm (BCD: unsupported) and its auto breaking is already good.
