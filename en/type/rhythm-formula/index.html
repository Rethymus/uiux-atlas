Line-height Rhythm

baseline rhythm · line-height snapping · vertical rhythm · CLREQ line spacing

Line-height × font-size = baseline multiples: compute density first (lh = fs×m), then snap to the grid half-step (lh = round(fs×m/unit)×unit) — multiplication sets tension, addition sets order, with hard constraints for CJK.

Web Standard ★★
Live demo official default
Parameters
Geometry▾
fontSize16px
px

Font size fs (px). Default 16 = the web body anchor (source of the least-common-multiple half-step that keeps 8pt grids and 48px touch targets compatible); 17 in the demo is Apple's official iOS Body size.

multiplier1.5

Line-height multiplier m (unitless). Default 1.5: 16×1.5=24 lands exactly on the 4px grid (verified by running); community band: body 1.5–1.75, headings 1.2–1.4 (convention, unverified as spec values); under 1.2 body text crowds, over 2 paragraphs scatter.

Motion▾
unit4

Baseline snapping unit (px). The 4px half-step is Material's 4dp baseline translated to web — 16px type, 24px leading and 48px targets all compatible; the 8px step is stricter but often pushes leading off the density optimum.

Structure & DOM

The demo is a body block with a rhythm ruler: the text renders at the real fs/lh, and translucent rules are drawn line by line at the snapped leading — “line boxes stacking row by row” made visible, with raw and snapped readings side by side:

<div class="rh-block" style="font-size:16px; line-height:24px">
  <span class="rh-line" style="top:24px"></span><!-- one rhythm rule every 24px -->
  <p>Density from size × multiplier; order from snapping to the half-step.</p>
</div>
<code>raw: 16 × 1.5 = 24px → snap(4) = 24px (Δ0, lands natively)</code>

Key points:

  • The leading is an exact px value (snapped from fs×m) and the rhythm rules repeat at that same px interval — rules and line boxes must coincide, any offset means the formula is wrong;
  • Three readings: raw fs×m, snapped round(fs×m/unit)×unit, plus the delta Δ and the post-snap effective multiplier;
  • The CLREQ floor check gets its own row: body ≥1.5×, ruby ≥1.5× (verbatim spec doctrine).

Styling & Parameters

Three parameters (fontSize/multiplier/unit), all JS-type, run live by the demo (research 14 §7; verified by running: 16×1.5=24 ✓; 15×1.5=22.5 → snap(4)=24 ✓):

① Density → rhythm, in two steps:

lineHeight(px) = fontSize × multiplier        multiplier sets relative density
lh = round(fs × m / unit) × unit              density first, then snap the rhythm (lh ≡ 0 (mod unit))

② Zero-dependency JS:

const snap = (v, u = 4) => Math.round(v / u) * u;
const baselineLH = (fs, m, u = 4) => snap(fs * m, u);
const cjkLH = (fs) => Math.max(1.5 * fs, fs + 8);   // CLREQ print constraint as the web floor
baselineLH(16, 1.5);  // 24 — verified ✓
baselineLH(15, 1.5);  // 24 (22.5 snapped, airier wins) — verified ✓

③ CSS realization:

.prose { font-size: 16px; line-height: 1.5; }        /* unitless: 16→24, 20→30 */
.prose  p + p { margin-top: 24px; }                  /* paragraph gap = one rhythm unit */
.prose  h2 { font-size: 25px; line-height: 32px; }   /* big type, smaller ratio (1.28), px snapped to 4px */

Where the numbers come from: the 16px anchor and 4px half-step translate Material’s official “8dp base + 4dp half-step, type on the 4dp baseline grid” to the web; the mixed-script floor = CLREQ §5.6.1 ‘single-side binding line spacing shall not be less than half the font size’ (total leading ≥1.5×) and §5.5.3.2 ruby ≥1.5× the base size; Apple’s iOS Body 17/22, Footnote 13/18 are the official measured table (research 13 §1.3); the web mixed-script 1.5–1.75 band is community convention (unverified as a spec value).

Motion & Interaction

  • Adjust the multiplier: m from 1.5 to 1.25 at 16px gives a raw 20px leading — already on the 4px grid, Δ0; at 1.4 you get 22.4 → snapped 24, Δ+1.6, “airier wins”; the snapping trade-off is transparent in the Δ reading;
  • Change the size: 17 (Apple Body) × 1.294 = 22 — but 22 is not a multiple of 4, so it snaps to 24 (Δ+2): the official 22px leading itself ignores the 4px grid, a real divergence between platform measured tables and engineering grids, shown as-is;
  • Switch the snap unit: unit 4 → 8 pushes small sizes (11–13px) onto much coarser steps — the reason the half-step exists, at a glance;
  • Rhythm rules redraw instantly with the parameters; no autonomous animation, entrance fade respects prefers-reduced-motion.

Real-world examples

  • Apple’s iOS text style table: Body 17pt/22pt (ratio ≈1.294), Footnote 13/18 (≈1.385), Caption 1 12/16 (≈1.333) — the official measured table shows big type taking smaller ratios, small type larger, a converging ladder (research 13 §1.3, Typography.md Specifications);
  • Ant Design’s leading formula: in genFontSizes.ts source, lineHeight = (fontSize + 8) / fontSize — base 14 → leading 22, i.e. “add 8px absolutely” rather than “multiply a fixed ratio”, paired with the log-derived type ramp (research 13 §3.4, source verified line by line);
  • CLREQ’s hard CJK constraints: W3C’s Requirements for Chinese Text Layout sets single-side binding line spacing ≥ half the font size (total leading ≥1.5×), ruby contexts ≥1.5× the base size, and horizontal measure ≤48 characters — the legal-grade basis for Chinese product leading tokens (research 14 §7.3, quoted verbatim from the spec).

Working doctrine: 16×1.5=24px is the greatest common denominator; big type smaller ratios, body larger, all px on the 4px grid; pass 1.5× before tuning density for mixed scripts; write multipliers unitless so they inherit across sizes. Sibling entries: vertical-rhythm (the full rhythm system), baseline-grid (the 4px half-step itself), modular-scale-math (where the sizes come from), cjk-typography (the rest of CLREQ in practice).

When to use 4
  • Design-system leading tokens: size scale × multiplier band, all snapped to the 4px half-step
  • Mixed CJK/Latin body text: hold the CLREQ floor (≥1.5×) before tuning density
  • Card/list line tiers: leading as the rhythm unit, paddings as integer multiples
  • Long-form layout: leading, paragraph gaps and heading margins share one rhythm unit (the math inside vertical-rhythm)
When not to use 4
  • Reusing px line-heights across sizes — a px leading does not scale when inherited
  • Giving headings body multipliers (1.5+) — large type wants smaller ratios (1.2–1.4) or the heading block bloats
  • Snapping unit ≥ the leading itself — an 8px unit on 11px type explodes small text
  • Ruby/pinyin under 1.5 leading — CLREQ's ruby context requires ≥1.5× the base size; lower and the annotations collide
Accessibility

WCAG 1.4.12 text spacing requires layouts to survive user-set leading at 1.5× the font size — unitless line-height with snap headroom is the prerequisite; leading ≥1.5 doubles as the low-vision readability floor; for CJK large-text equivalence see the contrast entry. Leading is not decoration: cramped values (≤1.2) measurably slow readers with dyslexia.

Browser support

line-height and spacing snapping is pure CSS math, supported everywhere; half-leading control (leading-trim) is not yet broadly shipped (proposal stage per community sources) — half-leading distribution currently follows font metrics, so cross-font alignment needs measured tuning.

Fallback

There is no compatibility fallback to speak of; the real risk is snapping too hard — 15×1.5=22.5 snapped to 24 'prefers airier leading' (the conventional direction), but snapping to 20 loses the breathing room. Pin the direction: round always toward readability.

Sources 3

Origin'Sizes multiply ratios for hierarchy; line-heights snap to 4px for rhythm' is web-typesetting craft convention (research 14 §7, marked as practitioner consensus); the CJK hard constraints come from W3C's CLREQ: single-side binding line spacing ≥ half the font size, ruby contexts ≥1.5× the base size (quoted verbatim from the spec); the web mixed-script 1.5–1.75× band is community practice with no single authority (unverified, stated as such); Apple's iOS text styles (17/22 etc.) are official measured values (research 13 §1.3).
