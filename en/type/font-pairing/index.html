Font Pairing

字体组合 · 衬线搭配 · typeface pairing · serif × sans

Serif × sans contrast pairing, or the single-family multi-weight strategy: contrast, separated duties and restraint — two typefaces at most, and question the third.

Three demo pairings: serif × sans (classic contrast), the reversed pairing (magazine-style serif body), and single-family (Inter Variable weights only, per Apple HIG's one-family principle). The serif in the first two modes is a system stack (Georgia → Songti/SimSun → serif), zero third-party dependencies.

Code breakdown

Structure & DOM

No special structure — two (or one) voices, each in its place:

<article class="card">
  <p class="kicker">Kicker</p>
  <h2 class="head">Serif headline</h2>
  <p class="body">Sans body text…</p>
  <blockquote class="quote">The quote follows the headline side</blockquote>
</article>
/* Classic contrast: the serif owns the mood, the sans owns reading */
.head, .quote { font-family: Georgia, "Times New Roman", "Songti SC", SimSun, serif; }
.body         { font-family: system-ui, sans-serif; }

/* Single-family strategy (Apple HIG): one family site-wide, hierarchy via size / weight / color */
.head { font-weight: 650; }
.body { font-weight: 400; }

Key points:

  • The font-family list always ends with a generic serif/sans-serif — it falls through level by level and never depends on a single font name;
  • CJK serif coverage: Georgia has no CJK glyphs, so the list names Songti SC (macOS) / SimSun (Windows) before the generic — the exact serif look varies by platform;
  • Separated duties: the display family is used only at large sizes; the body family must pass a long-form reading test (rule of thumb, unverified).

Styling & Parameters

Three parameters: pairing (JS-type) plus heading size/weight (CSS-variable type):

.fp-h2 {
  font-size: var(--fp-head-size);      /* 34px */
  font-weight: var(--fp-head-weight);  /* 600 */
  line-height: 1.15;
}
[data-pairing="serif-head"] .fp-h2 { font-family: Georgia, …, serif; }
[data-pairing="single"]     .fp-h2 { font-family: inherit; } /* weight only */

Where the numbers come from — with honest labeling:

  • Apple HIG Typography: “Minimize the number of typefaces you use”, one family site-wide, hierarchy via size/weight/color only (research 01, HIG original verified) — the official basis of the single-family strategy;
  • Vercel ships Geist as four same-source families, Sans/Serif/Mono/Pixel, OFL 1.1 (research 05 §25) — the official instance of “same family, many voices”;
  • This site’s sans + mono duet: --font-sans: Inter Variable, Noto Sans SC… + --font-mono: JetBrains Mono… (src/styles/global.css:150-152, spec §2.2: “mono only for numerals/counts/shortcuts”);
  • The pairing methodology details (contrast principle, prefer same-family multi-axis, no third typeface) are community practice, unverified — the Google Fonts Knowledge “Choosing type” page is JS-rendered and its body could not be verified (research 12 §9, recorded as such).

Motion & Interaction

  • Strategy switch: the pairing param swaps three pairings via data-pairing; the serif/sans re-costume is an instant reflow (font-family changes involve no animation);
  • Weight experiments: in single-family mode, dragging headingWeight 300→900 is driven by Inter Variable’s real wght axis (not synthesized bolding); on the serif modes, values beyond the system stack’s 400/700 get clamped or synthesized — the demo shows that distortion as-is;
  • Size contrast: pull headingSize from 64px down to 24px and watch the pairing degrade into “body text with a different font” — this is how under-contrasted pairings fail;
  • No prefers-reduced-motion branch: the demo has no animation, everything is an instant reflow.

Real-world examples

  • Apple HIG and the SF system: the official “Minimize the number of typefaces you use” plus one SF family site-wide, hierarchy through size differences plus weight differences (Headline uses Semibold against a same-size Body, research 01, verified from the HIG original) — the strongest endorsement of the single-family strategy.
  • Vercel Geist: distributed as four same-source families Sans/Serif/Mono/Pixel, verified from the official README (research 05 §25) — a family lineup that answers “serif headline × sans body” as one coherent set.
  • This site, uiux-atlas: the sans + mono duet (sans for UI and prose, mono only for numerals/counts/shortcuts) is written into spec §2.2 and implemented in the --font-sans/--font-mono variables (src/styles/global.css:150-152) — the engineering version of “no third typeface after duties are separated”.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
pairingthe serif modes buy mood, the single family buys consistency; no all-purpose option, only different duty splits“no pairing” (system defaults) also has consistency, but gives up the two-voice expressiveness
headingSizestronger contrast and a more audible serif temperament; too large squeezes the bodybelow ~24px the headline stops reading as a different voice — the pairing degrades into decoration
headingWeightin single-family mode 700+ separates hierarchy from the 400 body (real wght axis)below 300 legibility drops on light backgrounds; serif values beyond 400/700 are clamped or synthesized

Working rules: assign the duties first (who owns mood, who owns reading), then pick families; two at most; carry hierarchy with size (≥1.5×), weight and color at once. Treat methodology details as community consensus and validate key decisions with a long-form reading test.

When to use 4
  • Editorial/magazine pages: serif display headlines over sans body — mood and readability split the duties
  • Product-site heroes: sans display plus a body family consistent with the brand voice
  • Tool products' single-family strategy: one variable family with size/weight/color carrying hierarchy (Apple HIG principle)
  • Long-form reading: any body candidate must pass a long-form reading test first (rule of thumb, unverified)
When not to use 3
  • Stacking three or more typefaces — adding a third after duties are separated is an explicit methodology violation (community consensus, unverified)
  • Two near-identical voices in a 'fake pairing' — without contrast readers sense mess, not hierarchy (community practice, unverified)
  • Using a display family for long body text — display fonts are not designed for small-size reading
Accessibility

Never encode hierarchy in the family alone — Apple HIG requires size/weight/color to participate (research 01, verified); serif headings at ≤300 weight lose legibility on light backgrounds; serif body at small sizes on low-DPI screens needs real testing; metric mismatches in the fallback stack can reflow text (pair with the font-display-strategy entry's fallback thinking).

Browser support

No modern CSS dependency: font-family/font-weight are the most basic capabilities; system serif stacks (Georgia/Songti/SimSun/generic serif) work everywhere but the exact serif glyphs vary by platform; variable weights need a wght axis (already shipped by this site's Inter Variable).

Fallback

Always end the font-family list with a generic (serif/sans-serif): the list falls through level by level — CJK serif lands on system serifs like Songti where Georgia lacks CJK glyphs, then the generic serif; never depend on a single font name. Synthesized weights can look smudgy — clamp key hierarchy to weights the font actually ships.
