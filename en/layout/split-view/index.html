Split View

分栏面板 · 可拖分栏 · Resizable Panels · Split Pane

A draggable divider splits the UI into two resizable panes: drag and arrow keys drive one shared value, while container queries re-flow pane content — the backbone of IDEs, mail clients and docs sites.

%

%

The clamp floor for drag and arrow keys (JS-type; also written to the divider's aria-valuemin). Default 20% is a demo baseline value, unverified; pane content should collapse rather than be crushed below the floor — the demo uses a container query to stack the right card when it gets too narrow.

Code breakdown

Structure & DOM

Split view has no native CSS standard (research 05 §8); the DOM is simply “left pane + divider + right pane” as three siblings, where the divider is a real interactive element, not a decorative line:

<div class="split">
  <div class="pane pane-left">File tree…</div>
  <button
    type="button"
    role="separator"
    aria-orientation="vertical"
    aria-valuemin="20" aria-valuemax="80" aria-valuenow="40"
    aria-label="Resize panes"></button>
  <div class="pane pane-right">Preview card…</div>
</div>

Key points:

  • The divider carries role="separator" + tabindex="0" + arrow keys — the WAI-ARIA separator minimum, the same semantics react-resizable-panels uses per its README (research 05 §8);
  • The left pane’s width is the single state; the right pane flexes to fill; aria-valuenow and the visual width share one value;
  • The right pane declares container-type: inline-size, so pane content adapts via @container — once “split” links up with “container queries”, narrowing the pane visibly re-flows the card;
  • MDN Cookbook’s “Split navigation” is a visually divided nav recipe, not desktop-style resizable panes (research 05 §8).

Styling & Parameters

Two parameters — the initial pane width and the clamp floor — injected as --sv-start and consumed as JS state for clamping:

.split { display: flex; }
.pane-left {
  width: var(--sv-start, 40%);   /* initial 40%: demo baseline, unverified */
  min-width: var(--sv-min, 20%); /* clamp floor 20%: demo baseline, unverified */
  flex: none;
  transition: width 0.15s ease;  /* smooths the param slider only; drag writes directly */
}
.pane-right { flex: 1; min-width: 0; container-type: inline-size; }

/* Pane linkage: the query condition must be a literal (container queries reject custom properties) */
@container (max-width: 280px) {
  .pane-right .card { flex-direction: column; }
}

Where the numbers come from:

  • Defaults 40% / 20% are this entry’s demo baseline values, unverified — react-resizable-panels defaultSize/minSize are product-specific with no single official value;
  • The divider hit area is ≥10px wide with touch-action: none to stop touch-scroll hijacking; the 2px focus ring sits on the divider itself;
  • The 280px container breakpoint is also a demo baseline — in production derive it from the card’s own collapse width.

Motion & Interaction

Dragging is the primary interaction; the keyboard is its equal, both funnelling through one clamp function:

  • Drag: Pointer Events + setPointerCapture; during the drag width updates directly (no transition); touch-action: none makes it draggable on touch;
  • Arrow keys: ←/→ step ±2% (Shift ×3), Home/End jump to the clamp limits — the step is a demo baseline; aria-valuenow updates on every step;
  • Double-click reset: back to the startSize default, reusing the store’s reset();
  • Width transition: a 0.15s ease smooths slider-driven changes; dropped under prefers-reduced-motion;
  • The container-query linkage is layout feedback, not animation: the card flips instantly with no tween — the user controls the width, and animation would only get in the way.

Real-world examples

  • react-resizable-panels (research 05 §8): the origin of the ecosystem’s de-facto standard itself — <PanelGroup>/<Panel> grouping, a drag handle, WAI-ARIA separator keyboard support with gridline enhancement, verified first-hand from the README; most web renditions of the VS Code-style resizable pane are built on it or the same semantics (specific adoption lists not individually verified);
  • IDE and mail-client two-pane shells: editor file tree + editing area, mail list + reading pane — the most typical split products, all with draggable dividers and double-click reset (editorial summary — per-product implementation parameters not individually verified);
  • The MDN Layout Cookbook: the official recipe closest to this topic is “Split navigation” (visually grouped nav) — research 05 §8 explicitly notes it is not the same concept as resizable panes; don’t conflate them when researching.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
startSizewidens the left pane so file names fit; the right pane hits the 280px container breakpoint sooner and the card stacksgives the right pane the stage; preview cards spread horizontally; long file names truncate (overflow: hidden covers it)
minSizeguarantees both panes stay readable but shortens the drag travel; too high and the split loses its pointmore freedom to squeeze; below ~15% narrow-pane content gets crushed — the demo’s container-query flip is the safety net

Rules of thumb: set the floor to “the width where the narrow pane is still legible”, not a symmetric percentage; prefer a generous divider hit area (≥10px); the panes’ DOM order never changes with the drag, so screen-reader order stays stable.

When to use 4
  • IDE file trees beside editors, mail clients' list beside the reading pane
  • Docs sites and admin sidebars users can narrow to taste
  • Comparison surfaces: image editors side-by-side, log viewers
  • Density adaptation inside panes — container queries re-flow cards as the pane narrows (this demo's linkage)
When not to use 4
  • Phone-portrait primary UIs — thumb-dragging a divider is error-prone; just stack
  • Content that must be fully visible (reports, forms) — squeezing panes truncates key info
  • Mistaking MDN Cookbook's 'Split navigation' (visually divided nav) for resizable panes — different concepts (research 05 §8)
  • Dividers as mouse-only targets — no keyboard equivalent violates WCAG 2.1.1 (the separator pattern in research 05 §8 exists for exactly this)
Accessibility

The divider is a WAI-ARIA separator: role="separator", tabindex=0, aria-orientation="vertical", aria-valuenow/min/max tracking the pane width live, arrow keys to adjust (same semantics as react-resizable-panels' README, research 05 §8); aria-valuenow updates during drag; the clamp floor keeps either pane's content reachable; pane re-flow changes visuals only, never DOM order (WCAG 1.3.2); a visible focus ring sits on the divider; pane-width transitions are dropped under prefers-reduced-motion.

Browser support

What the demo relies on — Pointer Events, role="separator" and container queries — is broadly available; container queries are Baseline Widely available since 2023-02 (research 05 §6). Split panes have no native CSS standard — the ecosystem solution react-resizable-panels inherits React's compatibility surface (research 05 §8).

Fallback

Environments without drag/pointer support (keyboard, screen readers) must keep an arrow-key equivalent — role="separator" + tabindex + arrow keys is the WAI-ARIA separator minimum (research 05 §8); on very narrow viewports drop the split and stack vertically (media queries take precedence); where container queries are unsupported, pane content keeps its default stacked layout without errors.
