M3 Dynamic Color

Material You 动态取色 · Dynamic Color · 动态取色流程

From one source hue, expand five palettes per a variant recipe, then map role tones into primary/on-primary/container semantics — light and dark share the same tokens.

The HCT hue of the source color — the scheme's single input. Default 299 = the HCT hue of the M3 baseline seed purple #6750A4 (measured 298.98 with the embedded CAM16 forward model; research 06 §7 records #6750A4 as the official light primary). HCT hue scales differ from hsl/oklch: oklch blue ≈ 220°, HCT blue near 300°.

varianttonal-spot

Variant = the recipe that builds the five key palettes (chroma levels + hue rotations; constants from the published scheme_*.js): tonal-spot = primary(h,36)/secondary(h,16)/tertiary(h+60,24)/neutral(h,6)/NV(h,8), default since Android 12; neutral = 12/8/16/2/2, near-grayscale; vibrant = primary(h,200, clamped to what is achievable) with secondary/tertiary rotated via breakpoint tables for maximum colorfulness; expressive = primary(h+240,40) with neutrals shifted +15°, deliberately detached from the seed hue. Variant names and timeline (Android 12: Tonal Spot; Android 13: Neutral/Vibrant/Expressive) per research 06 §6.

schemelight

Light/dark: the same role tokens read different tones (library convention at contrastLevel 0) — accents 40↔80, containers 90↔30, on-colors 100↔20 or 30↔90, surfaces 98↔6. Official hand-tuned baseline for reference (research 06 §7): light primary #6750A4 / on-primary #FFFFFF / primary-container #EADDFF / error #B3261E / surface #FFFBFE / on-surface #1C1B1F; dark primary #D0BCFF (≈tone 80) / on-primary #381E72 / primary-container #4F378B / surface-variant #49454F — reflecting the 'darker-mode accents get brighter and less saturated' convention. Variant-generated values sit close to but not exactly on the hand-tuned baseline (baseline primary palette chroma≈48 vs 36 in the variant pipeline; neutral≈4 vs 6).

Code breakdown

Structure & DOM

Dynamic color is a pipeline, not a CSS property: source color → five key palettes → role tokens. On the web it lands as two same-named sets of CSS variables (light/dark), with components referencing role names only:

<body data-scheme="light">
  <button class="md-btn">Continue</button>
</body>
body { background: var(--md-surface); color: var(--md-on-surface); }
.md-btn { background: var(--md-primary); color: var(--md-on-primary); }
body[data-scheme="dark"] { --md-surface: #141218; /* …the whole mapping swaps */ }
  • Role names come in three families: accents (primary/secondary/tertiary/error), surfaces (surface/surface-variant/…), and containers + on-X inverses (primary-container ↔ on-primary-container) (research 06 §7);
  • Components never write concrete colors — Android’s own framing is “assign color roles via design tokens, not specific values” (matching the 3-layer token architecture in research 06 §2.10);
  • on-roles track their base: after switching scheme or variant the whole set must be recomputed — never swap primary without swapping on-primary.

Styling & Parameters

The variant builds the palettes; the scheme decides each role’s tone (library convention at contrastLevel 0):

// Variant recipes (constants from material-color-utilities 0.3.0 scheme_*.js)
tonalSpot:  primary(h,36) secondary(h,16) tertiary(h+60,24) neutral(h,6) nv(h,8)
neutral:    primary(h,12) secondary(h,8)  tertiary(h,16)    neutral(h,2) nv(h,2)
vibrant:    primary(h,200→clamped) secondary(rot(h),24) tertiary(rot(h),32) neutral(h,10) nv(h,12)
expressive: primary(h+240,40) secondary(rot(h),24) tertiary(rot(h),32) neutral(h+15,8) nv(h+15,12)
// Role tone mapping (material_dynamic_colors.js, contrastLevel 0)
primary 40/80 · on-primary 100/20 · primary-container 90/30 · on-primary-container 30/90
surface 98/6 · on-surface 10/90 · surface-variant(NV) 90/30 · outline(NV) 50/60

Where the numbers come from:

  • Official hand-tuned baseline (research 06 §7, Android docs colors.xml values): light primary #6750A4, on-primary #FFFFFF, primary-container #EADDFF, error #B3261E, surface #FFFBFE, on-surface #1C1B1F; dark primary #D0BCFF (≈tone 80), on-primary #381E72, primary-container #4F378B, surface-variant #49454F;
  • Variant-generated values sit close to but not exactly on the baseline: the baseline primary palette has chroma≈48 while tonal-spot uses 36; baseline neutral≈4 vs variant 6 (the demo shows both side by side, without pretending);
  • The error palette is fixed at (hue 25, chroma 84) (dynamic_scheme.js constructor);
  • The wallpaper→source chain (quantize Celebi = Wu + WSMeans → score) is in research 06 §6; the demo starts at the source hue;
  • In the full flow one wallpaper derives 5 schemes forming the light/dark theme basis (research 06 §6); the demo reduces this to three inputs — source hue + variant + scheme — to expose the generation rules themselves;
  • Brand-color retention: HarmonizedColors aligns custom colors toward the system hue in HCT, keeping contrast and visual balance (runtime applyToContextIfAvailable(), research 06 §6).

Motion & Interaction

  • Any of the three params recomputes the whole role set instantly; light/dark is the same roles at different tones, not an inversion (Apple HIG’s dark-mode guidance: dark themes are “not necessarily inversions”, with Android Force Dark as the counter-example — research 06, item 13);
  • Swatch transitions animate only background-color/color (0.18s); removed under prefers-reduced-motion;
  • A mini UI card assembled from the generated surface/on-surface/primary/secondary-container makes the role semantics verifiable at a glance;
  • The role tone table shown here is the library’s contrastLevel 0; contrastLevel ±1 further adjusts via contrastCurve and toneDeltaPair (including pushing tones out of the awkward 50–59 zone) — a parameter this entry does not expose (dynamic_color.js source);
  • Light/dark switching should never shift layout: roles only affect color/background, never size — one more reason to keep theme and component layers decoupled;
  • Across variants the most sensitive are vibrant (primary chroma 200, clamped per achievable tone) and expressive (primary hue +240°) — drag sourceHue and watch roles “jump”.

When to use 4
  • Whole-app theming from wallpaper/brand color: one source hue in, five palettes plus the full role token set out
  • Light/dark sharing semantic tokens: components write var(--md-primary) only, themes swap mappings (isomorphic to the 3-layer token architecture)
  • Product themes with different personalities: tonal-spot follows, neutral restrains, vibrant shouts, expressive leaps
  • Brand-color retention: HarmonizedColors aligns custom colors toward the system hue in HCT, keeping contrast and balance
When not to use 3
  • Treating generated values as the official baseline: #6750A4 is hand-tuned (chroma≈48) while the tonal-spot pipeline uses 36 — close, not equal
  • Checking contrast only in dark: on-roles take different tones per scheme — verify both
  • Bypassing roles and painting UI with arbitrary palette tones: role tones carry contrast constraints, random tones break readability
Accessibility

Role tones carry contrast constraints (library contrastLevel 0): an on-color ≥50 tones from its base guarantees ≥4.5:1 body text (AA); a ≥40-tone gap guarantees ≥3:1 for non-text/large text. primary vs. surface is held at ≥3:1 by contrastCurve(3,4.5,7,7). After changing variant/scheme, re-verify the critical pairings (button text/base, text/background) instead of assuming they hold; WCAG thresholds never round up.

Browser support

Roles land as hex/CSS variables usable in any browser; on Android the system applies them at runtime via DynamicColors. The demo's palette and role computation is an embedded TS port (material-color-utilities ships C++/Dart/Java/Swift/TypeScript/Kotlin implementations) with no CSS feature dependency.

Fallback

On the web, generate both role token sets at build time (--md-primary/--md-on-primary/…) and switch via prefers-color-scheme or a theme class; in environments without variable switching, fall back to a single fixed theme. Output whole role values; no runtime interpolation.
