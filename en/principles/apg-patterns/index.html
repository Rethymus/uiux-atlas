WAI-ARIA APG Patterns

ARIA Authoring Practices · APG 模式库

The W3C ARIA Authoring Practices provides 30 component patterns; each ships keyboard interaction plus ARIA roles/states/properties in three sections — the first reference for building custom components.

Code breakdown

Structure & DOM

The demo is an APG 30-pattern browser: a chip wall on the left plus a “three-section spec” card on the right:

<div class="apg-chips" role="group" aria-label="APG pattern list">
  <button class="apg-chip" aria-pressed="true">Button</button>
  <!-- ×30 -->
</div>
<aside class="apg-card" aria-live="polite">
  <h4>Button</h4>
  <b>Keyboard</b> …
  <b>roles</b> …
  <b>states & properties</b> …
</aside>

Key points:

  • The 30 pattern names come verbatim from the research 07 §34 list (Accordion … Window Splitter; Slider and Multi-Thumb listed separately make exactly 30);
  • Every card keeps the APG pattern page’s fixed three-section structure: keyboard interaction / roles / states & properties (07 §34 verbatim);
  • Key hints cover only the six patterns verified in research 07 §36 (Button, Checkbox, Radio Group, Slider, Tabs, Dialog); the rest honestly read “see the APG pattern page” — nothing invented.

Styling & Parameters

const visible = PATTERNS.map((p, i) => ({ p, i }))
  .filter(({ p }) => group === "all" || p.group === group);
  • group filters across five tiers (all / forms & input / navigation & menus / containers & disclosure / composite & feedback) — a teaching grouping, not an official APG taxonomy (the APG page doesn’t group), stated as such in the schema and here;
  • keyhint toggles the key hints; the card is aria-live="polite" so switches reach screen readers;
  • Chips are real buttons with aria-pressed for selection — “selection ≠ focus” placed in both visuals and semantics (07 §35).

Motion & Interaction

  • Clicking a chip swaps the card content (no animation — for spec reading, instant switching is best); aria-live announces it;
  • Tab walks all chips with intact focus rings; the container has role="group" + label;
  • No looping animation; no reduced-motion handling needed.

Real-world examples

  • The working draft for custom Tabs / Trees: the APG’s Tabs and Tree View pattern pages give the full tables for roving focus, aria-selected, and arrow-key behavior — most component-library docs list props, not keys; APG is the authoritative fill for that layer (07 §34/§35);
  • Combobox’s four autocomplete behaviors: APG specifies list/manual/both/none separately — the spec source behind research 07 §5 (the combobox’s four autocomplete behaviors);
  • Dialog’s Esc and trap conventions: WebAIM’s keyboard page (07 §36) and the APG Dialog pattern corroborate each other — “modal traps are legitimate, but Esc should usually release, focus returning to the opener” is now the de-facto standard for modal implementations (see the keyboard-navigation entry).

The lesson: use APG as “check before you build, verify after” — treat the 30-pattern list as a coverage checklist for custom widgets: if your component is in the library, copy its three sections; if it isn’t, then you may invent.

When to use 3
  • The first spec to read before building composite widgets (radio group, tabs, tree)
  • The authoritative supplement when a component library's docs lack a keyboard section
  • Reviewing custom widgets: check roles/states/properties against the pattern page item by item
When not to use 2
  • Treating ARIA attributes as magic that auto-provides keyboard behavior — ARIA declares semantics; authors implement behavior (07 §35)
  • Mixing patterns (a dialog with menu behavior) without re-checking the spec
Accessibility

This entry is about accessibility itself: demo cards are real buttons with visible focus rings and labeled groups; key hints carry only verified content, deferring to 'see the APG pattern page' where unverified.

Browser support

Pure DOM interaction; the demo is itself a miniature APG reference implementation (focusable card buttons with intact focus rings).

Fallback

APG is a spec document — nothing to degrade; the engineering exit: read the pattern page's keyboard section before building a custom widget, then walk it keyboard-only (see the keyboard-navigation entry).
