Keyboard Navigation

键盘无障碍 · 焦点管理 · focus management

Tab/Shift+Tab moves between components, arrow keys move inside composites (roving focus); focus indicators stay visible, focus is never lost, and modal traps must release via Esc and return focus.

Web Standard ★★★
Live demo official default
Parameters
Motion▾
scenetoolbar

JS-type param (the demo subscribes and swaps scenes). toolbar = roving tabindex + arrows; tabs = Tab in/out + arrow selection (preloaded panel, selection follows focus); dialog = Tab trap + Esc release + focus returned to the opener (the full 07 §35/§36 set).

ringnative

Focus indicator style. native = leave the browser default outline alone (07 §35: don't strip default outlines casually); strong = a 3px high-contrast solid ring (--kn-ring-width), the compliant form of custom focus rings (≥3:1 non-text contrast, SC 1.4.11).

Geometry▾
ringWidth3px
px

Strong-ring width. Default 3px: more salient than the common 2px outline; raise it to test ring legibility over busy backgrounds.

Code breakdown

Structure & DOM

The demo combines three keyboard scenes + a skip link + a key log:

<button class="kn-skip">Skip to main content</button>
<div class="kn-scene" tabindex="-1">
  <!-- toolbar: role="toolbar" + roving tabindex -->
  <!-- tabs: role="tablist"/"tab"/"tabpanel" -->
  <!-- dialog opener -->
</div>
<span class="kn-live" aria-live="polite"></span>

Key points:

  • Skip link: hidden off the stage top (translate: -200%), slides in on keyboard focus — the canonical “first Tab stop” form (WebAIM: long pages need skip links);
  • Toolbar: role="toolbar" + roving tabindex (active item tabindex=0, the rest -1); Tab enters once, arrows move inside (07 §35’s Tab/arrows division of labor);
  • Tabs: panels preloaded → selection follows focus on arrow keys (07 §35’s only condition for it); the aria-selected fill and the focus ring are two different visuals — focus ≠ selection;
  • Dialog: aria-modal="true" traps (two focusables cycle with Tab/Shift+Tab), Esc closes and returns focus to the opener — the full 07 §36 key table.

Styling & Parameters

.demo-stage { --kn-ring-width: 3px; }
.kn-skip:focus-visible { translate: -50% 0; }      /* appears on focus */
.kn-field[data-ring="strong"] …:focus-visible {
  outline: var(--kn-ring-width) solid oklch(0.45 0.16 260);
  outline-offset: 2px;
}
  • ring defaults to native: the browser default outline stays untouched (07 §35 verbatim: don’t strip default outlines casually); strong demonstrates the compliant custom ring — solid, ≥3:1 non-text contrast (SC 1.4.11);
  • ringWidth defaults to 3px (cssVar --kn-ring-width);
  • Switching scenes (the scene param) resets that scene’s internal state, preventing cross-scene state leaks.

Motion & Interaction

  • The skip link slides in with a 0.15s translate transition — itself a keyboard-first motion example; harmless under reduced-motion (the position change is the information);
  • The key log writes “pressed → what happened” into the right panel and announces via aria-live="polite" — focus movement is silent to screen readers; the log supplies the narrative;
  • Opening the dialog focuses its first button; closing calls openerRef.focus() — both sides of 07 §35 “focus must persist”;
  • Every scene completes keyboard-only; Tab order: skip link → scene controls → (trapped inside while the dialog is open).

Real-world examples

  • GitHub’s keyboard-first interface: pressing . inside a repo opens web VS Code, t opens the file finder — single-key shortcuts plus a command palette as the pinnacle of keyboard navigation (editorial generalization, echoing heuristic ⑦ “shortcuts for experts”, 07 §21);
  • Component-library Dialog implementations (the Radix/shadcn family): scale+fade overlay entrance, focus returned to the trigger on close, Esc to release — the same family verified in the motion/overlay-entrance entry, with keyboard behavior per the APG Dialog pattern (07 §34/§35);
  • WebAIM’s mobile reminder: “test on mobile devices with an external keyboard” — tablet plus external keyboard is the most overlooked real keyboard environment (07 §36 verbatim).

Parameter Sensitivity

ParameterTurning it up…Turning it down…

The lesson: the whole checklist is six items — visible (focus ring), reachable (don’t strip tabindex, <a> with href), ordered (Tab order = reading order), never lost (return on close), escapable (Esc releases traps), predictable (no focus grabbing on load). Clear all six and SC 2.1.1/2.1.2/2.4.7/2.4.3 come within range.

When to use 3
  • Implementing roving focus in custom composites (radio group/tablist/menu/listbox/grid)
  • Modal dialogs: trap + Esc + focus return, the trio
  • Focus placement after deleting items or closing panels (back to trigger or next item)
When not to use 3
  • `outline: none` with no replacement indicator — an explicit WebAIM anti-pattern
  • Grabbing initial focus on page load (unless the page has one main function nearly everyone uses immediately)
  • 'Selection follows focus' on non-preloaded panels (with loading lag, the two must decouple)
Accessibility

This entry IS accessibility: focus indicators must be visible (leave default outlines alone; color/gradients can vanish in high-contrast mode, SC 1.4.11 ≥3:1); focus must persist; focus (= document.activeElement) and selection (= aria-selected=true) must be distinct in both visuals and semantics; keyboard traps are legal but Esc should release (SC 2.1.2); WebAIM reminds: test on mobile devices with an external keyboard.

Browser support

Roving tabindex, :focus-visible, and the dialog trap logic are standard DOM/ARIA capabilities in all modern browsers; :focus-visible is Baseline.

Fallback

No browser feature to fall back; the engineering red-line list (07 §35/§36): ① never `outline:0/none` away the focus indicator; ② no `tabindex≥1`; ③ no tabindex on non-interactive elements; ④ `<a>` without href isn't keyboard-reachable; ⑤ closing overlays must return focus; ⑥ modal traps must release via Esc (SC 2.1.2); ⑦ long pages need skip links, heading hierarchy, landmarks.

Sources 2

OriginW3C ARIA APG keyboard interface practices (research 07 §35) + WebAIM keyboard accessibility conventions (07 §36). Core rules: Tab vs arrows division of labor, visible focus indicators (never strip default outlines casually), persistent focus (after closing dialogs or deleting list items, set focus back to the trigger or the next item, or it drops to body), predictable focus movement (no initial focus on page load), focus ≠ selection (visually distinct); the key table: button Enter/Space, checkbox Space, radio arrows, dialog Esc/trap/return, slider arrows+Home/End, tabs Tab in/out + arrow selection. WCAG Level A requires focus to be able to leave via keyboard (2.1.2).
