ThemeShadow (Fluent)

主题阴影 · Fluent elevation shadow · ThemeShadow

Fluent ThemeShadow: a preset shadow driven by the element's z coordinate (elevation), auto-adapting to light, theme and surroundings; non-Popup usage must declare Receivers, and only rectangular shadows are supported.

Fluent ★★
Live demo official default
Parameters
Geometry▾
elevation8

The shadow-casting element's z coordinate (DIP, elevation). Larger z = more diffuse, fainter shadow — the exact curve is auto-adjusted by the system per light/theme/surroundings, and Fluent publishes no per-step numeric table. The default 8 is the demo scale set by this batch's spec: research records no official default z; never cite it as an official value.

opacity100%
%

Overall shadow gain. The ThemeShadow API itself exposes no shadow opacity — strength is decided entirely by the system from z and surroundings; this parameter is a Web-approximation demo knob for comparing strengths, not part of the official API surface.

Code breakdown

Structure & DOM

ThemeShadow’s mental model is “elements float on a z axis, the system computes the shadow”: you declare only the element’s elevation (z coordinate), while blur, offset and strength are auto-decided from light, theme and surroundings. Who receives the shadow must be stated explicitly:

<!-- WinUI: XAML side -->
<Grid x:Name="RootGrid" Translation="0,0,8">
  <Grid.Shadow>
    <ThemeShadow />
  </Grid.Shadow>
</Grid>
<!-- Non-Popup usage: the receiving element must be declared -->
themeShadow.Receivers.Add(BackgroundGrid);

Key points:

  • z semantics: the third dimension of Translation (or UiElement.Translation) is elevation, in DIPs; Popup/Flyout/Dialog take ThemeShadow automatically, but every other element must add receivers to the Receivers collection or no shadow renders;
  • Rectangular shadows only — irregular shapes (circles, notched forms) need hand-tuned DropShadow (research 02 §C5);
  • The old Depth/depth-shadow design-guide pages have 404-migrated; depth semantics live in the ThemeShadow/DropShadow API pages (research 02 §7 erratum).

Styling & Parameters

The Web has no ThemeShadow; the demo approximates the “larger z = more diffuse, fainter” trend with box-shadow — an approximation, not Fluent’s real lighting algorithm:

.demo-stage {
  --theme-shadow-elevation: 8;   /* z value (unitless) */
  --theme-shadow-opacity: 100%;  /* demo gain; the real API has no such parameter */
}
.fl-card {
  /* blur/offset grow with z while alpha falls */
  box-shadow:
    0 calc(var(--z) * 0.4px)
      calc(var(--z) * 2.2px + 2px)
      color-mix(in srgb, black
        calc(clamp(0, var(--z) * 0.035, 0.5) * var(--theme-shadow-opacity)),
        transparent);
  border-radius: 8px;            /* ThemeShadow projects rectangles */
}
/* The param card: --z comes straight from the parameter */
.fl-card.param { --z: var(--theme-shadow-elevation); }
/* Comparison cards: fixed z steps 0 / 4 / 8 / 16 / 32 (inline --z) */

Where the numbers come from:

  • The z-as-elevation semantics, the Receivers collection and the rectangle-only constraint all come from the WinUI ThemeShadow API page (research 02 §C5, fetched firsthand);
  • No official “z → shadow parameter” table exists — system adaptivity is the selling point; the demo’s 0.4 / 2.2 / 0.035 coefficients are this entry’s Web trend-fit, honestly flagged in the body and in fallback;
  • The default z=8 is the demo scale set by this batch’s spec, not an official default.

Motion & Interaction

Fluent’s depth model treats z as an animatable quantity:

  • Lift/drop (z interpolation) is part of the hierarchy narrative: raise z temporarily while dragging, settle back on release; a smooth 150–250ms interpolation (the Web demo transitions the formula’s output), with the final state shown directly under prefers-reduced-motion;
  • On theme switches (light ⇄ dark) ThemeShadow recomputes itself; the demo offers light/dark canvases for comparison;
  • Never animate the shadow’s color/blur parameters directly — animate z (the semantic quantity) and let the formula derive the shadow; that is the Web-side echo of ThemeShadow’s “system computes shadows” intent.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
elevationmore diffuse, fainter, farther-offset shadow — “floating higher”; past 24 the weak-alpha large blur nearly vanishes on light canvases and offset alone carries the hierarchythe shadow tightens and hardens; near 0 it is indistinguishable from “stuck to the canvas”, and z=0 casts nothing (the first comparison card)
opacityfull-strength shadow — clear but heavy on light backgroundsthe whole shadow fades; 0% removes it (for comparison only — in production change z, never crush opacity)
(fixed semantics)—with Receivers unset, non-Popup elements get no shadow at all — not “fainter”, absent; check Receivers first when debugging

Rule of thumb: use steps 0/4/8/16/32 (overlay > card > base) and never more than 4 z levels per screen; on dark themes weak shadows lose legibility, so hierarchy must ride surface-luminance differences (brighter = forward) together with shadows.

When to use 4
  • WinUI/UWP overlays and card hierarchies: popups, flyouts and dialogs take ThemeShadow's environment-awareness for free
  • z values as the elevation language in cross-platform systems: 0/4/8/16/32 steps aligned with a Web shadow approximation
  • Drag lift: temporarily raise z while dragging, restore on drop — the canonical Fluent depth interaction
  • Theme-adaptive surfaces: ThemeShadow retunes itself per theme, no hand-written dual shadow sets
When not to use 4
  • Non-rectangular shadows — ThemeShadow is rectangle-only; irregular shapes require DropShadow (research 02 §C5)
  • Expecting shadows on non-Popup elements without setting Receivers — the receiving elements must be declared explicitly
  • Treating the Web demo's approximation as Fluent output — the two are not numerically interchangeable
  • Using heavier shadows to mean clickable — Fluent depth encodes hierarchy, not interactivity
Accessibility

Shadows are decorative depth cues: never the sole carrier of hierarchy or state (pair with position/size/text); on dark themes shadows lose legibility — Fluent adapts automatically, and the demo's dark-canvas form is for comparison only; shadows carry no interaction semantics, so focus still needs a visible indicator (WCAG 2.1 SC 2.4.7).

Browser support

ThemeShadow is a WinUI/XAML capability and does not exist in browsers; the Web demo approximates it with box-shadow (baseline everywhere). WinUI 3 ships it via Windows App SDK; the UWP namesake targets the older platform. This research pass did not audit a per-Windows-version availability matrix.

Fallback

The Web approximation fits the 'larger z = more diffuse, fainter' trend, not Fluent's real lighting algorithm — for cross-platform work, deliver the z semantics rather than specific shadow values; on WinUI, forgetting Receivers in non-Popup scenarios silently hides the shadow, the most common pitfall.
