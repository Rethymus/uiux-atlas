Tooltip & Legend

Chart Tooltip · Legend Positioning · 悬浮提示

The chart's two reading channels: the legend handles series lookup (right by default — ggplot2's source default), the tooltip handles precise values (ECharts defaults: mousemove trigger / 100ms hide delay), and WCAG 1.4.13 demands Esc-dismissibility, hoverability and persistence.

legendPosright

JS-type param (the demo subscribes and re-lays-out). right = ggplot2's source default (L262 legend.position = "right"); top = the common variant of Power BI's theme presets pushing bar-chart legends to BottomCenter; none = legend off, landing jfly's principle — the demo direct-labels series names above the first group (direct labeling beats distant color matching). ECharts legends support all four edges, but its default layout value was never verbatim-verified in source (annotated).

tooltipFollowon

JS-type param (the demo subscribes and switches positioning). on = the tooltip follows the pointer (matching ECharts' default triggerOn 'mousemove'); off = the tooltip docks at a fixed corner where the pointer can easily move into it — the strongest form of WCAG 1.4.13 Hoverable. Trigger/hide follow ECharts defaults: showDelay 0, hideDelay 100 (hiding waits 100ms after pointer-out, leaving a window to move into the tooltip).

Structure & DOM

Legend and tooltip are the chart’s “two reading channels”: the legend answers “whose line/bars are these”, the tooltip answers “what exactly is this value”. In the DOM the legend is normal flow (a top row or right column); the tooltip is an overlay.

<div class="chart-panel">  <!-- position: relative — the tooltip's positioning context -->
  <div class="legend legend--top">…swatch + series name…</div>
  <svg>…<rect class="bar" tabindex="0" aria-label="This year, Jan: 64" />…</svg>
  <div class="tooltip" role="status" hidden>
    This year · Jan  value: 64
  </div>
</div>

Key points:

  • The tooltip’s positioning context is the panel container (not body): follow mode converts clientX/Y - container rect; docked mode pins right/top — it can never escape the card;
  • Bars are focusable elements (tabindex=0 + aria-label) and focus triggers the same tooltip — WCAG 1.4.13 governs focus content equally, giving keyboard users the value channel;
  • Trade-off vs ECharts/D3: ECharts’ tooltip ships five defaults out of the box (trigger ‘item’ / triggerOn ‘mousemove|click’ / showDelay 0 / hideDelay 100 / transitionDuration 0.4, source-verified) plus four-edge legend placement; the hand-drawn demo exists to implement the 1.4.13 trio (Esc/hoverable/persistent) by hand — most chart libraries don’t fully satisfy all three, so audit item by item instead of trusting defaults.

}

Motion & Interaction

The tooltip is the easiest place to over-animate a chart — discipline first:

  • The trio (WCAG 1.4.13, Level AA): Esc closes instantly without moving pointer or focus; the pointer can enter the tooltip body without it vanishing; the tooltip persists until the pointer leaves trigger+tooltip, the user dismisses it, or the information goes stale — the demo implements all three and they pass as an acceptance checklist;
  • Appear/disappear: transitionDuration 0.4 (ECharts’ default) is an upper-bound reference; the demo shows/hides instantly; any transition animates only opacity/transform and is disabled under reduce;
  • Legend switches (top/right/none): flow re-layout with no animation — position-mode changes don’t cross-fade, or the legend “flies”;
  • The demo mounts its Esc listener only while the tooltip is visible — no resident window keydown.

Real-world examples

  • ECharts v5.5.1: the five tooltip defaults (trigger ‘item’ / triggerOn ‘mousemove|click’ / showDelay 0 / hideDelay 100 / transitionDuration 0.4) are verbatim in TooltipModel.ts; on the a11y side aria.label.enabled defaults on and aria.decal.show defaults off (v5.5.1 source verified).
  • ggplot2: legend defaults to the right (legend.position = "right", theme-defaults.R L262) and one theme statement moves it — the origin of the paradigm “legend position is a theme property, not a chart property” (source verified).
  • Power BI: official theme presets enumerate legend positions as BottomCenter/Right/Left/RightCenter, with the example pushing bar-chart legends to bottom-center; a Report Tooltips official doc page also exists (official docs verified / search hit).
  • jfly CUD guide: “For graphs and line drawings, label elements of the graph on the graph itself rather than making a separate color-coded key, since matching same colors in distant places is extremely difficult” — the academic original of direct labeling over legends (official page verified).

Parameter Sensitivity

ParameterTurning it up…Turning it down…
legendPosa top legend suits wide charts (horizontal room to spare); none saves the most space but hands lookup to direct labels — with many series the labels fight each otherright consumes a vertical column, trading chart height for legend width; cheapest with ≤4 short-named series
tooltipFollowfollow mode reads fastest, but the tooltip always sits 14px off the pointer — hard for magnifier users to enter (the weak form of 1.4.13 Hoverable)docked mode is Hoverable at its strongest, at the cost of the eye ping-ponging between bar and tooltip

Rules of thumb: desktop wide charts take right + follow; embedded minis take none + direct labels; any accessibility audit walks the “Esc / hoverable / persistent” checklist — library implementations get no exemption.

When to use 4
  • Series lookup on multi-series charts — legend docked top or right, swatches one-to-one with series
  • Precise value reading on interactive BI charts — mousemove-follow with a 100ms hide grace for fast scanning
  • Space-constrained embedded charts (mini charts in cards) — drop the legend for direct labels and reclaim its width
  • The template for accessibility audits — dismissible/hoverable/persistent is the WCAG 1.4.13 acceptance checklist
When not to use 4
  • Legends far from their swatches or paginated — jfly's own words: matching same colors in distant places is extremely difficult; direct-label when possible
  • Tooltips that cover the hovered point or vanish on approach — WCAG 1.4.13 failure F95 (not hoverable)
  • Tooltips without Esc dismissal that linger after the pointer leaves — failure F114 (not dismissible) / Persistent abused
  • Putting critical values only in the tooltip — touch and screen-reader users never get them; values need a second channel
Accessibility

WCAG 2.1 SC 1.4.13 (Content on Hover or Focus, Level AA) has three demands: (1) Dismissible — Esc closes it without moving pointer or focus; (2) Hoverable — the pointer can enter the tooltip body without it vanishing (for magnifiers and large cursors); (3) Persistent — it stays until the trigger is removed, the user dismisses it, or the information becomes stale. The demo implements all three: Esc listener + enterable tooltip + a 100ms post-out grace (ECharts hideDelay). Pairings: bars carry aria-label; the ECharts ecosystem adds aria.label auto-summaries for screen readers and aria.decal textures beyond hue.

Browser support

The demo uses native Pointer Events plus an absolutely positioned div — all modern browsers; no third-party positioning library like Popper (edge clamping is hand-written); the Esc listener is a window keydown active only while the tooltip is visible.

Fallback

Touch has no hover: the tooltip must also answer click/tap (ECharts' default triggerOn is already 'mousemove|click'); keyboard users: bars should be focusable and trigger the tooltip on focus (1.4.13 governs focus content equally); never let critical values live only in the tooltip — keep an alternative channel (direct labels / table).
