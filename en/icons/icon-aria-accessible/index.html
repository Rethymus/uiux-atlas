Icon Semantics & Accessibility

装饰性图标 · 图标可访问名 · aria-hidden · Accessible Icon · Decorative Icon

Decorative icons are removed from the accessibility tree with aria-hidden="true" and never sit on focusable elements; semantic icons get an accessible name describing the action ('search', not 'magnifying lens'); all four aria-hidden × name combinations compared against screen-reader behavior.

decorativeon

Decorative switch. Default on: the icon leaves the accessibility tree (MDN: aria-hidden="true" removes the element and all children from it) and the button announces only its accessible name — the MDN example itself splits work this way (decorated icon + named button). Red line: never put aria-hidden on a focusable element or its ancestor (focus would land inside a hidden subtree); here aria-hidden always sits on the svg while the button stays focusable (07 §4.1).

labelwith

Accessible-name switch. Default with: an icon-only button must carry a name describing the action, not the shape — WAI tutorial wording "'search' rather than 'magnifying lens'", "print this page" not "printer" (07 §4.1); the demo names it 「收藏」 (favorite), never 「star shape」. The without option shows the failure: an unnamed button reads just “button”, losing all information; for <img> without alt, screen readers may announce the file name/URL (inline SVG behavior varies by reader implementation, not standardized).

Code breakdown

Structure & DOM

Icon semantics split across two layers: the glyph layer (decorative or meaningful) and the interactive button layer (carrying the accessible name). The canonical split — decorative icons removed, focusable elements named:

<!-- Icon + text button: the visible text IS the accessible name; the icon is purely decorative (MDN's canonical split) -->
<button>
  <svg aria-hidden="true" viewBox="0 0 24 24">…star path…</svg>
  Favorite
</button>

<!-- Icon-only button: decorative icon + aria-label on the button, naming the action not the shape -->
<button aria-label="Favorite">
  <svg aria-hidden="true" viewBox="0 0 24 24">…star path…</svg>
</button>

Four iron rules (first-hand W3C/MDN, 07 §4.1):

  1. Purely decorative icons leave the tree: aria-hidden="true" removes the element and all children from the accessibility tree; hideable objects explicitly include “Purely decorative content, such as icons”;
  2. Red line: never aria-hidden on focusable elements, nor on their ancestors (hiding propagates down the tree and focus would land inside an invisible subtree);
  3. Precondition for removal: identical or equivalent meaning and functionality is already exposed to assistive technologies;
  4. Name the action, not the shape: the WAI tutorial prescribes “print this page” rather than “(image of a) printer”, “search” rather than “magnifying lens”.

Styling & Parameters

Both parameters are JS-type, driving real aria attributes on two live buttons; the simulation panel emits utterances from the same rule function:

// Decoration: aria-hidden always sits on the svg; the button stays focusable (red line intact)
<svg aria-hidden={decorative === "on" || undefined}>…</svg>

// Accessible name: "Favorite" (action), never "star shape"
<button aria-label={named ? "Favorite" : undefined}>…</button>

// Name computation (simplified accname): aria-label first, falling back to text content
const name = btn.getAttribute("aria-label") ?? btn.textContent.trim();

Motion & Interaction

This entry’s interaction is instant “configuration → behavior” feedback:

  • Parameters land on real buttons live: the svg’s aria-hidden and the button’s aria-label change together; the simulation panel and the matrix highlight the current combination;
  • Real keyboard behavior preserved: Tab focus, Enter/Space activation, a :focus-visible ring — which is itself bound by WCAG 1.4.11’s 3:1 (07 §4.3);
  • No motion in this demo, so prefers-reduced-motion needs no fallback;
  • The simulation panel is labeled a rule-based inference — it does not claim verbatim output from any reader (inline SVG announcements differ across NVDA/JAWS/VoiceOver).

Real-world examples

  • MDN’s aria-hidden example: decorated icon + text label carrying the name — the structural prototype of this entry’s icon+text button (07 §4.1);
  • W3C WAI Images Tutorial: functional-image alt text states intent (“search” rather than “magnifying lens”); an icon that merely accompanies link text gets alt="" (07 §4.1);
  • Current WAI-APG practice: after the old Images practice pages measured 404 in 2026-11, the duty moved to “Providing Accessible Names and Descriptions” and “Hiding Semantics with the presentation Role” — same substance: decorative removed, functional named (07 §4.2).

Parameter Sensitivity

ParameterTurning it up…Turning it down…
decorativeon removes the icon for clean announcements — but only while the button already carries an equivalent name; pair it with the name switch off and information instantly drops to zerooff keeps the icon in the tree — most readers skip untitled inline SVG anyway (varies by implementation), leaving uncertainty rather than added information

Anchors: decorative icons always aria-hidden and never on focusable elements; button names always state the action; confirm equivalent exposure before removing anything.

When to use 3
  • Icon + text button: icon purely decorative with aria-hidden, the text is the accessible name (MDN's canonical split)
  • Icon-only buttons (toolbars): icon aria-hidden + aria-label on the button stating the action (favorite / search / print this page)
  • Shared informational icons (e.g. new window): the alt text carries the icon's meaning itself (07 §4.1 example 3)
When not to use 3
  • aria-hidden on a focusable element or its ancestor — focus landing inside a hidden subtree is an ARIA red line (MDN, 07 §4.1)
  • Naming by shape ('star', 'magnifier') instead of by action ('favorite', 'search') — WAI tutorial, 07 §4.1
  • Hiding without equivalent information exposed — 'identical or equivalent meaning and functionality' is the precondition for removal (07 §4.1)
Accessibility

This entry IS the accessibility content: decorative icons leave the tree via aria-hidden; icon buttons get action-named accessible names; removal presumes equivalent information is exposed elsewhere. Adjacent guardrails: ≥3:1 non-text contrast (WCAG 1.4.11, see icon-color-states) and focus indicators bound by the same 3:1. The behavior table is a rule-based simulation; actual utterances vary by screen reader (marked honestly).

Browser support

aria-hidden and aria-label are standard ARIA attributes supported by modern browsers and major screen readers (NVDA/JAWS/VoiceOver/Narrator); how a given reader treats untitled inline SVG varies by implementation (not standardized) — the demo's simulation follows W3C/MDN rules and does not claim to replicate any specific reader verbatim. · widely available

Fallback

Very old assistive tech may ignore ARIA, so prefer native mechanisms for names: real text inside the button (visible label) beats aria-label; without ARIA a decorative icon degrades to one extra meaningless utterance and never breaks function — which is why MDN's example keeps the text label.

Sources 3

OriginThe rule backbone is first-hand W3C/MDN: MDN's aria-hidden page lists "Purely decorative content, such as icons" among hideable objects and forbids use on focusable elements; the W3C WAI functional-images tutorial requires alt text to convey intent — "'print this page' rather than '(image of a) printer'" (out/design-study/07-icons.md §4.1).
