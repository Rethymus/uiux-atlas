Web Haptics (Vibration API)

振动反馈 · navigator.vibrate · haptics · Vibration API

navigator.vibrate(pattern) is the web's only haptic channel: a millisecond count or a vibrate/pause alternation array, canceled by 0 or an empty array; it needs sticky user activation and is not Baseline (iOS Safari: no-op). Pulse-count semantics can mirror HIG's three preset families (Selection single pulse / Success two pulses / Error four pulses), but the ms values are officially unspecified.

Code breakdown

Structure & DOM

Haptics have no DOM — it is one API call plus a synchronized visual echo. The call must sit inside a user-gesture event handler; the visual echo (timeline bar / beat dots) gives users without vibration hardware or on unsupported platforms the same information:

<button id="done">Done</button>
// sticky user activation: call synchronously inside click/pointerup handlers
done.addEventListener("click", () => {
  navigator.vibrate([100, 60, 100]); // vibrate 100ms → pause 60ms → vibrate 100ms (demo values)
});
// cancel: vibrate(0) or vibrate([])
cancelButton.addEventListener("click", () => navigator.vibrate(0));

Key points:

  • pattern is a millisecond count (single pulse) or a vibrate/pause alternation array (multi-pulse), with no trailing pause;
  • Pulse count is the semantics: mirror HIG’s three preset families — Selection one pulse, notification success two, error four (officially only counts/categories are recorded; no platform publishes milliseconds);
  • When the API is missing (iOS Safari) or hardware absent (desktops) the call is ignored — so the visual echo is not decoration, it is a parallel information channel.

Styling & Parameters

Three JS-type params (pulses / on / off); the demo subscribes, builds the pattern, and drives the visual pulse in sync:

const pattern = [];
for (let i = 0; i < pulses; i++) {
  pattern.push(on);                       // vibrate slots (odd)
  if (i < pulses - 1) pattern.push(off);  // pause slots (even), no trailing pause
}
navigator.vibrate(pattern); // inside a gesture handler

Where the numbers come from: the array form, the SOS morse example ([100,30,100,…]), cancellation, truncation, and the activation constraint all come from MDN’s Navigator.vibrate page (research 04 §5.2); pulse-count semantics from Apple HIG “Playing haptics” (success = two pulses, warning = two, error = four; Selection = one short pulse; impact in five grades, research 04 §2.3/§5.2). The on/off defaults (100/60ms) are demo values, officially unspecified; iOS’s real waveforms come from system presets, with no web counterpart.

Platform notes (MDN’s wording): not Baseline; a no-op on iOS Safari; overly long patterns are truncated (implementation-defined cap); devices may stay silent in muted/DND modes.

Motion & Interaction

  • Vibration and visuals fire together: every playback lights the timeline bar and beat dots in sync — HIG’s “match visual/audio intensity” put into practice;
  • Cancellation is demonstrable: vibrate(0) stops instantly (the API form of HIG’s “must be disableable”);
  • Capability, honestly labeled: the demo detects navigator.vibrate; without it only the visual pulse plays and the UI says so — it never pretends a vibration happened;
  • Rhythm semantics: pauses too short smear a multi-pulse pattern into one long buzz, erasing “four pulses = error”; pulses too short (20ms-grade) go unfelt on most devices;
  • Sparingly: HIG verbatim — occasional haptics are the ones that land; on high-frequency actions they depreciate fast (for the visual side of press feedback see press-feedback).

Real-world examples

  • iOS system controls: HIG records that iOS toggles/sliders/pickers automatically play system haptics (research 04 §2.6) — “value change = one pulse” is the system default; web components align to it via navigator.vibrate;
  • Task-result feedback: HIG’s notification trio (success/warning/error) exists precisely for operation outcomes, fired in sync with toasts/dialogs (research 04 §2.3; for the toast scenario see toast-spring);
  • Android web: MDN is explicit that the API is not Baseline and is a no-op on iOS Safari — Android-family browsers are where web haptics are actually felt (research 04 §5.2); desktops often expose the API without any vibration hardware, which is exactly why the demo feature-detects.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
pulsesmore pulses carry heavier semantics: 2 = success, 4 = error per HIG; past 4 leaves the official semantic table and reads as noiseone pulse degrades to Selection semantics; pulse count is also the main driver of total duration (see off)
onheavier single pulses; past 200ms a pulse approaches one long buzz, the metaphor shifting from “tap” to “thud”at 20ms-grade most devices barely register it — the haptic exists in name only (MDN gives no floor; the figure is folklore, unverified)
offlonger gaps make the segmentation legible at the cost of linearly longer patternsgaps too short smear the pulses into one buzz and the count semantics vanish

Selection rule of thumb: pick the pulse count first (semantics), then tune on/off; total = pulses×on + (pulses−1)×off, and result feedback should stay in the hundreds of milliseconds; always ship a synchronized visual echo and label on/off honestly as demo values.

When to use 3
  • Physical confirmation of task results: two pulses for success, four for failure — fired in sync with the visual toast (HIG notification semantics)
  • Short confirmation on value changes: a single pulse for pickers/sliders/segmented controls (HIG selection semantics)
  • Physical metaphors: a view snapping into place, heavy objects colliding — impact in five grades (light/medium/heavy/rigid/soft)
When not to use 4
  • Anything beyond occasional use — HIG's own words: sparingly, or it stops registering; vibrating on every tap erases haptics altogether
  • Making haptics the sole carrier of key information — HIG: must be disableable and matched to visual/audio intensity
  • Expecting iOS Safari users to feel anything — the API is a no-op there (MDN); never bet functionality on it
  • Stacking vibration while camera/gyroscope/microphone are active — HIG notes vibration can interfere with those sensors
Accessibility

Haptics must be disableable and never the sole channel for key information (HIG verbatim; the web practice is vibration plus a simultaneous visual state); playback must originate from a user gesture (sticky user activation); the demo's visual pulse gives users without vibration hardware or support the same information; devices may stay silent in muted/DND modes (MDN) — never depend on the vibration event itself to convey information.

Browser support

Not Baseline (stated on the MDN page): some major browsers lack it — iOS Safari is a no-op; Android-family browsers support it; desktops may expose the API with no vibration hardware at all. Truncation caps and muted/DND behavior are implementation-defined (MDN's wording); the exact version matrix was not audited in this pass. The demo feature-detects: without navigator.vibrate it falls back to a visual pulse, honestly labeled.

Fallback

Three honest fallback tiers: (1) no API (iOS Safari etc.) or no vibration hardware (desktops) → a visual pulse animation stands in, functionality unchanged; (2) sticky user activation — the call must sit inside a user-gesture handler, which the demo's play button is; (3) devices may stay silent in muted/DND modes (MDN), where the visual channel still carries. Haptics are never the sole channel for key information (HIG: sync with visual/audio).
