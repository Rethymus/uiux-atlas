Smoothness Craft

高性能动画 · compositor-friendly · will-change 纪律 · velocity preserve

Smoothness is craft, not parameters: animate only transform/opacity, write transform directly per frame, treat will-change as a last resort removed after use, and hand interruption to physics springs — same animation, different craft, wildly different frame rates.

Web Standard ★★
Live demo official default

JS param (interrupt-handoff contrast). spring = Motion physics springs continuing from the current value + velocity (docs: 'incorporate the velocity of any existing gestures or animations'); tween = duration animation restarting from rest, ignoring velocity (docs: 'starts from rest and ignores velocity') — a perceptible hitch on mid-flight re-targets.

Code breakdown

Structure & DOM

The demo is two craft-contrast lanes + an FPS panel:

  • Lane A (property contrast): a box ping-pongs on a 2s sine, with the loop writing transform: translateX or left per frame (param-switched); the same rAF loop measures mean frame delta and >25ms long frames;
  • Lane B (interrupt handoff): one box, and a “re-target mid-flight” button compared across spring (velocity handoff) and tween (restart from rest) modes.
<div class="sm-lane"><!-- lane A -->
  <div class="sm-box"></div>  <!-- rAF writes style.transform / style.left per frame -->
</div>
<div class="sm-lane"><!-- lane B -->
  <motion.div class="sm-interrupt" style="x"></motion.div>
</div>

Key points:

  • Lane A demonstrates the correct per-frame posture — writing el.style.transform directly, never through CSS variables (per-frame variable changes invalidate the whole subtree’s styles, research 10 §7.4);
  • The FPS panel measures inside the same rAF loop, adding no extra listeners;
  • Lane B’s motion value is driven by a Motion spring; animate() naturally continues from the current value + velocity.

Styling & Parameters

Three JS-type enum parameters:

// Lane A: property switch (per-frame writes)
if (prop === "left") box.style.left = `${x}px`;            // triggers layout/paint
else box.style.transform = `translateX(${x}px)`;           // compositor path
// layerHint (layer promotion, MDN discipline: last resort, set before animating, removed on animationend)
box.style.willChange = hint === "will-change" ? "transform" : "auto";
// translateZ(0) promotion (the cheap fallback for older browsers, web.dev)
box.style.transform = `translateX(${x}px) translateZ(0)`;

// Lane B: two interrupt semantics
animate(x, next, { type: "spring", stiffness: 300, damping: 25 }); // physics spring: inherits current velocity
animate(x, next, { duration: 0.7, ease: "easeOut" });              // duration: restarts from rest (ignores velocity)

Numbers and conclusions (research 10 §7, all first-hand sources fetched this session):

  • Animate only transform/opacity: web.dev’s high-performance animations guide — anything else triggers layout/paint; the top/left demo drops 50% of frames vs 1% for the transform version (Chrome FPS panel measurement); blur/shadow paints are costlier;
  • will-change (MDN, point by point): “last resort — do not use preventively”; overuse → excessive memory + more complex rendering → slower; creates stacking contexts early; the correct posture is set via JS before the animation, removed on animationend; the cheap fallback without support is transform: translateZ(0);
  • Interrupt handoff: Motion docs verbatim — physics springs “incorporate the velocity of any existing gestures or animations”; duration-based springs “start from rest and ignore velocity” (research 10 §7.3);
  • Baking springs into linear(): Baseline 2023-12; linear(0, 0.25 75%, 1) dense sampling approximates any curve (Jake Archibald’s generator ships a Spring preset) (research 10 §7.5);
  • 60/120Hz: rAF callbacks match the display refresh rate (60/75/120/144Hz common); always write durations in ms, never in frames (research 10 §7.6).

Motion & Interaction

  • Property contrast: switching to left immediately worsens the panel’s long-frame count/mean delta (the small stage limits magnitude; the direction matches web.dev’s 50%/1% measurement);
  • Interrupt handoff: launch lane B’s box, then hit “re-target mid-flight” — the spring glides around (velocity preserved) while the tween re-accelerates from rest (a perceptible hitch);
  • Layer hints: the will-change/translateZ lanes follow MDN’s discipline — teaching switches only, never resident in production;
  • Reduced motion: lane A goes static (no per-frame writes), lane B lands directly; the FPS panel keeps working;
  • Performance: both lanes animate transform (Motion’s motion value writes styles directly, no CSS variables in the loop).

Real-world examples

  • react-hot-toast / sonner: container/key layers carry will-change: transform (verbatim in react-hot-toast source) — the legitimate “single resident container” scenario (research 10 §5.1/§7.1);
  • web.dev’s high-performance CSS animations guide: the top/left vs transform 50%/1% frame-drop comparison is Google’s official baseline experiment; “0 ms in the Rendering row of the Performance panel” is the acceptance bar (research 10 §7.1);
  • Jake Archibald’s linear() easing generator: MDN’s “See also” pick — bake the spring into linear() to get “the math spring’s shape hosted by compositor animations” (research 10 §7.5).

Craft checklist (run before writing code): animate only transform/opacity; write transform directly per frame, keep CSS variables event-level; will-change last-resort and removed after; physics springs for handoffs; durations always in ms; bake springs into CSS via linear() sampling.

When to use 4
  • A craft preflight before any animation: transform/opacity only — translate for travel, scale for sizing, opacity for visibility
  • Per-frame gesture driving: write el.style.transform directly (or a Motion motion value); CSS variables only at event level
  • Animations needing mid-flight re-targets (follow, drawers, slot pills): physics springs or visualDuration so velocity hands over
  • Performance reviews: 0ms in Chrome's Performance panel Rendering row is the acceptance bar; durations always in ms across 60/120Hz
When not to use 4
  • Animating top/left/width/margin — layout every frame; use FLIP (transform inversion) when layout must change
  • Resident will-change across many elements — MDN: excessive memory + more complex rendering can be slower; it also creates stacking contexts early
  • Driving subtree styles through per-frame CSS variable writes — inherited propagation invalidates the whole tree (research 10 §7.4)
  • Writing durations as frame counts ('run 12 frames') — rAF follows refresh rate, halving durations at 120Hz; use ms
Accessibility

The craft demo carries no sole information (textual readouts everywhere); static output under prefers-reduced-motion; continuously animating elements must not obscure content; the FPS panel is a teaching tool — in production you fix performance rather than acclimate users; large/flashing motion always offers an off switch (HIG Motion: cancellable).

Browser support

All crafts are Baseline: transform/opacity compositor animation, will-change (CSS Will Change Module), translateZ, rAF (MDN: callbacks match refresh rate, 60/75/120/144Hz common); baking springs via linear() is Baseline 2023-12 (research 10 §7.5/§7.6).

Fallback

Under prefers-reduced-motion the per-frame loop goes static and the interrupt lane lands directly; the FPS panel keeps working (pure measurement, not animation); every demo effect has a textual readout fallback — nothing depends on motion alone.
