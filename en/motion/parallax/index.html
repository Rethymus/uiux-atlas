Parallax

视差 · parallax scrolling · 多层滚动速率差

Depth from per-layer scroll-rate differences: background layers follow scrolling slower than the foreground (follow ratio p, 0 = pinned to viewport, 1 = synced with content), implemented per layer with scroll() timelines of scroll-driven animations that can run off the main thread; reduced-motion renders the static layers.

Web Standard ★★★
Live demo official default
Parameters
Geometry▾
rate0.3

The follow ratio p of the farthest layer: the layer moves p × the scrolled distance. 0 = pinned to the viewport (max parallax); 1 = synced with the foreground (no parallax). Mid/near layers derive as p×2, p×3 capped at 1 (demo layering). No official value — 0.3 is a demo value (community layering clusters at 0.2–0.6, unverified).

Motion▾
modecss

Implementation contrast: css mode uses declarative animation-timeline: scroll() — per the official article, declarative scroll-driven animations can run off the main thread; js mode uses a main-thread scroll event + rAF writing transform directly, which the same page notes runs on the main thread, async to compositor scrolling and prone to jank. Without scroll() support, css mode falls back to the js path with a label.

Code breakdown

Structure & DOM

Parallax is “one scroll container + one layered world”: the scroller carries all content, and inside .world three decorative layers (far/mid/near) stack under a real content layer that scrolls 1:1:

<div class="scroller">          <!-- overflow-y: auto, the only scroll source -->
  <div class="world">           <!-- relatively positioned, tall enough to create scroll distance -->
    <div class="layer far"  aria-hidden="true"></div><!-- decorative layers carry no content -->
    <div class="layer mid"  aria-hidden="true"></div>
    <div class="layer near" aria-hidden="true"></div>
    <div class="copy">…</div>   <!-- content layer scrolls 1:1, always readable -->
  </div>
</div>

Key points:

  • Decorative layers are pure backdrop (aria-hidden, pointer-events: none) — no body copy ever lands on a parallax layer;
  • Each layer gets a multiplier m (far 1 / mid 2 / near 3); the follow ratio is p = min(rate × m, 1); the content layer is always p=1;
  • Translation “compensates” against scrolling: the layer travels p × distance, so its on-screen net speed is p-fold — the smaller p, the closer to pinned.

Styling & Parameters

Declarative implementation (the CSS-variable param rate → --par-rate; JS measures the scrollable distance into --par-s):

@supports (animation-timeline: scroll()) {
  .layer {
    animation: drift linear both;
    animation-timeline: scroll(nearest block); /* must come after the animation shorthand */
    animation-duration: auto;                  /* duration belongs to scroll progress */
  }
}
@keyframes drift {
  from { transform: translateY(0); }
  to   { transform: translateY(calc((1 - min(var(--par-rate) * var(--px-m, 1), 1)) * var(--par-s))); }
}

The JS contrast path (the official article’s legacy route): scroll events + rAF writing el.style.transform — it runs on the main thread, async to compositor scrolling, and janks under fast scrolling; declarative scroll() can run off the main thread (research 04 §4). The demo’s mode param stages exactly this contrast; browsers without scroll() fall back to the JS path automatically, with a label.

Where the numbers come from: all mechanics come from Chrome’s official scroll-driven animations article (research 04 §4); no official follow-ratio value exists — the demo default of 0.3 is a demo value (community layering clusters at 0.2–0.6, unverified); Firefox/Safari support status was explicitly not audited in the research, deferring to the MDN compatibility table.

Motion & Interaction

  • Rate difference is depth: while scrolling, the far layer tracks at 30% (default), mid at 60%, near at 90%, content at 100% — a three-step speed gradient visible on one screen;
  • Two boundaries, p=0 / p=1: 0 = the far layer is pinned (the starfield never moves); 1 = every layer syncs with content (no parallax); the demo labels both;
  • JS/CSS live contrast: switch to js mode and feel the smoothness difference — the official conclusion (main thread vs compositor) becomes tangible;
  • Performance: animate transform only; --par-s is measured once at mount/resize, so the scroll path reads no layout;
  • reduced-motion: under reduce the parallax switches off entirely and the static composition renders (the JS path stands still too), content unaffected.

For scroll-timeline basics (progress bars, reveals, animation-range) see scroll-driven-animations; for parallax inside transitions (iOS forward/backward) see page-transitions.

Real-world examples

  • iOS forward/backward transitions: M3’s “Transition patterns” documents iOS hierarchy transitions using parallax — the background trails the foreground (research 04 §3.3), the official system-level proof that “rate difference = depth”;
  • Chrome’s official scroll-driven docs: list “parallax background images” as a canonical scroll()-timeline use case (foreground/background moving at different speeds via different timelines/ranges, research 04 §4) — the declarative pattern shown here is the officially recommended implementation;
  • Multi-layer marketing heroes (community-common, unverified): starfield/mountain/foreground layers riding at different rates are common on web marketing pages but lack a dedicated spec — the research states plainly that “no dedicated primary-source article on parallax was found” (research 04 §8.5); treat the scroll-driven article as the only primary source.

Parameter Sensitivity

Selection rule of thumb: content stays 1:1 forever; parallax is for decoration only; start rate at 0.3 and tune by “how slow should the far layer trail”; prefer declarative scroll() over scroll events whenever supported.

When to use 3
  • Multi-layer backdrops on marketing/narrative pages (starfields, mountains, skylines) — slower backgrounds create depth
  • Depth layering on cards/heroes: decorative layers ride along at derived p×2/p×3 rates while content stays 1:1 readable
  • Depth cues inside system transitions — iOS forward/backward transitions ship parallax (background slower than foreground, per M3 transition docs)
When not to use 4
  • Body copy or data on parallax layers — text moving at layer speed hurts readability; parallax layers carry decoration only
  • Full-screen parallax across an entire page (the visionOS-derived guidance explicitly avoids full-screen parallax, research 11 §5)
  • Driving many layers from JS scroll events — main-thread per-frame writes jank under fast scrolling (same official page); prefer declarative scroll()
  • Shipping parallax without a reduced-motion fallback — a vestibular safety red line (MDN, research 04 §6.1)
Accessibility

Parallax must honor prefers-reduced-motion (under reduce, static layers render and the JS path keeps still); parallax layers carry no key information (pure decoration, aria-hidden); sustained large-area displacement is a common vestibular trigger (MDN), and HIG adds that motion must be cancellable and never the sole channel for key information; visionOS-derived guidance: keep key content in the mid-viewport safe area and avoid full-screen parallax (research 11 §5).

Browser support

scroll()/view() timelines: the official article snapshot covers Chrome/Edge 115+ (research 04 §4); Firefox/Safari status was explicitly not audited in the research — defer to the MDN compatibility table. The demo therefore feature-detects and falls back to a JS path with a label. prefers-reduced-motion: Baseline since 2020-01 (research 04 §6.1).

Fallback

Two-tier fallback: (1) without animation-timeline: scroll() support the demo switches to a JS path automatically (rAF + scroll events writing transform), keeping the parallax; (2) under prefers-reduced-motion: reduce the parallax switches off entirely and every layer renders in a static composition — parallax is a classic vestibular trigger, and content never depends on the parallax layers.

Sources 2

OriginChrome for Developers' "Scroll-driven animations" (Bramus, fetched, research 04 §4) lists "parallax background images" as a canonical scroll-driven use case: foreground/background layers move at different speeds via different timelines/ranges; the mechanics (scroll()/view() timelines, duration auto, animation-timeline after the animation shorthand, declarative implementations can run off the main thread) are from the same page. The research notes no dedicated primary-source article on parallax exists (research 04 §8.5); iOS's foreground/background transition parallax is separate (research 04 §3.3). No official value exists for the follow ratio p.
