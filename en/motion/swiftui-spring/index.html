SwiftUI Spring

Apple 弹簧 · response/dampingFraction · .spring()

SwiftUI's .spring(response:dampingFraction:blendDuration:) two-parameter spring: response is the time-scale of stiffness (seconds), dampingFraction the ratio of critical damping — the source of iOS' native feel.

Apple HIG ★★★
Live demo official default
Parameters
Geometry▾
response0.5s
s

The time-scale of the spring's stiffness, expressed as an approximate duration in seconds (Apple: 'response is... the stiffness expressed as an approximate duration'; 0 means infinitely stiff, suited to interactive driving). Official default 0.5s (Apple DocC). Higher = slower and stickier; lower = snappier, approaching interactiveSpring territory.

dampingFraction0.825

The fraction of the damping needed for critical damping (Apple: 'dampingFraction is... the fraction of the amount of damping needed to achieve critical damping'). Official default 0.825: slightly under-damped, with a hint of overshoot on arrival. 1 = critically damped, no bounce; below 1 the bounce grows as the value drops; under 0.5 oscillates visibly; above 1 overdamped, crawling to the target.

Motion▾
presetsnappy

Apple's spring preset family, officially defined as duration 0.5s + base bounce: bouncy = 0.3, snappy = 0.15, smooth = 0 (Apple DocC, research 02 §A13). The demo's top lane drives it with Motion's duration+bounce spring exactly per that definition, racing the bottom lane's custom response/dampingFraction spring. Defaulting to snappy is a demo choice, not an official 'default preset'.

Code breakdown

Structure & DOM

The demo runs two spring lanes side by side, launched together from the same start toward the same target: the top lane runs the preset (Apple’s official duration+bounce definition), the bottom lane the custom response/dampingFraction (converted into a Motion physics spring). Each lane needs only three DOM pieces:

<div class="ss-lane">
  <div class="ss-end ss-end-l"></div>
  <div class="ss-end ss-end-r"></div>
  <motion.div class="ss-ball" style={{ x }} />  <!-- x is the useMotionValue -->
</div>

Key points:

  • The ball’s position rides a useMotionValue driving transform: translateX; calling animate() on the same MotionValue launches or interrupts;
  • Both lanes share one launch entry (button, lane click, or Enter) so the feel difference is compared on one shared timeline;
  • The readout shows the converted stiffness/damping (bottom lane) and the preset bounce (top lane) live, keeping numbers and feel in one-to-one correspondence.

Styling & Parameters

All three parameters are JS-typed (no CSS variables); the demo subscribes to the store and assembles Motion transitions:

// SwiftUI response/dampingFraction → Motion stiffness/damping conversion:
// the standard equivalence of a damped harmonic oscillator (mass = 1) —
//   stiffness = (2π / response)²
//     (Apple: response is the stiffness expressed as an approximate duration ≈ natural period, ω₀ = 2π/response)
//   damping = 4π × dampingFraction / response
//     (Apple: dampingFraction is the fraction of the damping needed for critical damping, ζ = c / (2√(km)))
// Note: this conversion is derived from physics; neither Apple nor Motion publishes an official cross-formula.
const stiffness = (2 * Math.PI / response) ** 2;            // default 0.5s → ≈ 157.9
const damping = (4 * Math.PI * dampingFraction) / response; // default 0.825 → ≈ 20.7
animate(xCustom, target, { type: "spring", stiffness, damping, mass: 1 });

// Top lane: presets exactly per Apple's official definitions (duration 0.5s + base bounce)
animate(xPreset, target, { type: "spring", duration: 0.5, bounce: bounceOf(preset) });

Where the numbers come from (Apple DocC, verified via the official docs JSON data endpoint; research 02 §A11/A13 and 04 §1.3B agree):

  • response official default 0.5s, dampingFraction official default 0.825 (blendDuration defaults to 0 and is not a parameter of this entry);
  • Official preset definitions: bouncy = duration 0.5s + bounce 0.3, snappy = 0.5s + 0.15, smooth = 0.5s + 0;
  • Parameter semantics are Apple’s own wording: response = stiffness as an approximate duration, dampingFraction = fraction of critical damping.

Motion consumes the conversion: motion.dev documents type:"spring" taking stiffness/damping/mass (defaults 1/10/1, see the motion-spring entry) — the same family as SwiftUI’s system but on different axes, so never pass values across directly; always convert.

Motion & Interaction

  • Side-by-side race: tapping “Launch” (or either lane / Enter) sends both balls to the same target — snappy vs the custom 0.5/0.825, or bouncy’s extra hops, readable at a glance;
  • Params apply live: dragging response/dampingFraction interrupts the bottom spring mid-flight and continues from the current position (Motion physics springs inherit the current value’s velocity per the docs); picking a preset switches the top lane’s bounce;
  • Why the control exists: presets live in the duration+bounce system (predictable total time) while response/dampingFraction live in the stiffness+damping system (transferable feel) — one ball per system turns that abstraction into a visible fact;
  • Reduced motion: under prefers-reduced-motion: reduce the animation is skipped and balls land on target immediately; the readout still shows the converted values;
  • Performance: only transform is animated (ball travel), honoring the web.dev floor (research 04 §1.5).

Parameter Sensitivity

Selection rule: matching iOS feel → response/dampingFraction (start from measured system values); matching a timeline → preset duration+bounce; conversions go through the damped-oscillator equivalence, never a direct hand-off.

When to use 4
  • Cross-platform replication of iOS' native feel: match system controls via response/dampingFraction
  • The 0.5s/0.825 default suits most overlays, cards and toggles; lower response first for snappier feel
  • Preset picking: bouncy for bounce, snappy for general interaction, smooth for none (official definitions in the param note)
  • Interactive, hand-following animation: lower response (0 = infinitely stiff, explicitly recommended for interactive driving)
When not to use 4
  • Continuous quantities like progress bars — no bounce belongs there (same caveat as the Motion spring entry)
  • Passing response/dampingFraction straight into Motion on the Web as if interchangeable — the parameter systems differ and must be converted
  • Springs on high-frequency small controls (checkboxes etc.) — Apple HIG: avoid motion on frequent interactions (research 04 §2.1)
  • Conflating the presets (bouncy/snappy/smooth) with response/dampingFraction — the presets are officially defined in the duration+bounce system
Accessibility

Springs are displacement motion — a common vestibular trigger: they must honor prefers-reduced-motion (the demo outputs the final state directly); never make users wait out a spring (HIG: motion is cancellable); stronger bounce (lower dampingFraction) amplifies displacement discomfort, especially for motion-sensitive users (research 04 §1.6/§6).

Browser support

The native API belongs to SwiftUI (iOS 13+); the Web-side equivalent rides on Motion's (formerly Framer Motion) physics springs — the two mainstream spring parameter systems (research 04 §1.3). The demo is a Web rendition: it requires JS, and elements stay at their initial position without it.

Fallback

Output the final state directly under prefers-reduced-motion (the demo detects via useReducedMotion and skips animation); motion is never the sole carrier of key information (HIG motion principles); consecutive spring animations keep their velocity — interruption is not a reset (research 04 §1.3B).
