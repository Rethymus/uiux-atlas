Theme Flip Stagger

卡片翻转换肤 · flip stagger · 元素级翻转 · 逐卡翻转换肤

Each card flips around its vertical axis (rotateY) to the 90° edge, re-skins at the moment it is invisible, and flips back flat — card after card on a stagger; total = duration + (n − 1) × stagger. No full-page snapshot performance: complementary to color/theme-transition (root snapshot) and motion/view-transitions (element-level view-transition-name).

Code breakdown

Structure & DOM

Element-level flip re-skinning performs no full-page snapshot show: each card flips around its vertical axis (rotateY) to the 90° edge — swapping its palette at the one instant it is invisible — then flips back flat, card after card on a stagger, like a row of cards re-dressing in sequence. Unlike color/theme-transition (whole-page root snapshot) and motion/view-transitions (element-level view-transition-name + snapshots), it needs no View Transitions API: pure CSS 3D keyframes + JS orchestration.

<div class="stage" data-fx-theme="dark" data-fx-duration="800">
  <div class="grid" style="perspective: 900px">
    <div class="card" data-face="light" data-phase="idle" style="--tf-sign: 1">…</div>
    <!-- ×n: one element per card; its palette rides on the data-face variable tables -->
  </div>
  <button data-fx-toggle>Toggle theme</button>
</div>

Key points:

  • The card is a single-faced element (no front/back pair): its palette is driven by data-face, and at the mid-flip 90° edge the element is zero-width, so the swap is invisible — no two-sided backface structure needed;
  • The flip splits into two CSS animations: out-leg rotateY 0→±90° (accelerate) → on animationend swap data-face and chain the back-leg ±90°→0 (decelerate) — the swap lands on the animationend frame (exactly 90°), never on a guessed setTimeout;
  • The stage’s data-fx-theme flips on click (contract), while each card’s face catches up only when it passes 90° — the staggered “re-dressing” reads precisely from that offset;
  • perspective sits on the grid container so all n cards share one vanishing point; each card carries its own --tf-sign for direction.

Styling & Parameters

Two palette variable tables plus two flip keyframes:

.card[data-face="light"] { --card: #fff; --fg: #1f2430; /* …light-face table */ }
.card[data-face="dark"]  { --card: #21252d; --fg: #eceff5; /* …dark-face table */ }

.card[data-phase="out"] { animation: flip-out var(--half-out) cubic-bezier(0.4, 0, 1, 1) forwards; }
.card[data-phase="in"]  { animation: flip-in  var(--half-in)  cubic-bezier(0, 0, 0.2, 1) forwards; }
@keyframes flip-out { to { transform: rotateY(calc(var(--tf-sign) * 90deg)); } }
@keyframes flip-in  { from { transform: rotateY(calc(var(--tf-sign) * 90deg)); } to { transform: rotateY(0deg); } }

Timing structure (computed live by the demo; data-fx-duration always carries the actual value):

per-card duration = out-leg half-out (40%) + back-leg half-in (60%)
total = duration + (n − 1) × stagger            ← n = card count
defaults: duration 500 (out 200 + back 300), stagger 60, n = 6 → total 800ms

Where the numbers come from (research 20):

  • Out-leg accelerate cubic-bezier(0.4, 0, 1, 1) / back-leg decelerate cubic-bezier(0, 0, 0.2, 1), asymmetric 200ms + 300ms: research §6.5’s element-flip recipe curves and durations (exit fast, enter slow = M3 §5; the timing skeleton matches Chrome’s shared-axis example on the same docs page, §1.1); the demo scales 200/300 proportionally at 40%/60% of duration;
  • stagger default 60ms: a demo orchestration choice with no official figure; the cascade mirrors the reveal family (15–30ms band, §6.3) and motion/stagger-orchestration (item i starts at i × delay, spread = delay × (n−1)) — a flip travels farther per card, so the value scales up;
  • rotateY/perspective work in every engine with no API dependency (see browserSupport).

Motion & Interaction

  • One click: the stage’s data-fx-theme flips immediately → card i starts flipping at i × stagger → the out-leg’s animationend (exactly the 90° edge) swaps data-face and chains the back-leg in the same batch → done when all cards land flat;
  • Interruption (re-click mid-animation): clear every timer, land all cards flat instantly at the pre-click theme (= the old run’s end state), then stagger toward the new target from there — matching “a new transition skips the old one to its end” (Chrome docs, research §1.1; re-click/skipTransition behavior verified on headless Edge, research 20a §S8); never stuck halfway;
  • Reduced motion: duration treated as 0 — every card swaps faces instantly, no rotation (WCAG 2.3.3/C39, research §5); matchMedia changes apply live;
  • Element-level VT is the same feel behind an API: research §6.5’s view-transition-name version (old snapshot flip-out 200ms / new snapshot flip-in 300ms) shares these curves and asymmetry; the API version pays a snapshot-capture cost (measured 57–94ms, research 20a §S9), while the pure-CSS version pays none — but must guarantee the face swap lands on 90° (that is exactly what the animationend hook buys);
  • Motion is enhancement only: the theme outcome is carried by color too, and survives motion being disabled (HIG “Make motion optional”, research §5).

Real-world examples

  • Chrome for Developers (View Transitions same-document page): the official reference for the exit-fast/enter-slow two-leg structure — the page’s Material shared-axis example (exit 90ms + main 300ms) established the asymmetric skeleton, and the element-level view-transition-name flip recipe (old snapshot flip-out 200ms / new snapshot flip-in 300ms, research §6.5) applies that same page’s mechanism directly;
  • Apple HIG Motion (iOS 26 Liquid Glass motion principles): a system-level constraint reference — “aim for brevity and precision in feedback animations”, “avoid adding motion to frequent interactions”, “let people cancel motion” (HIG motion page fetched as .md, research §4/§5); card-flip re-skinning is an occasional ceremonial feedback and falls inside that guidance’s scope. No specific product shipping per-card flip re-skinning was verified in the research, so none are listed.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
durationeach flip grows more leisurely; past 600ms a single card starts to drag (beyond M3’s large-area tier)under 300ms flips turn brittle, near a “flash swap”; with the out-leg squeezed under 100ms the swap frame may become perceptible
staggerspread = stagger×(n−1) lengthens and the roll-call rhythm sharpens; with large n the last card visibly waitsapproaches a whole-row simultaneous flip; 0 = all six flip at once and the stagger narrative disappears
directionalternate flips odd/even cards opposite ways — the most playful rhythm; one-way (right/left) gives the strongest, most restrained page-turn feel— (the enum’s two directions: one-way = restrained, alternating = playful; pick by page character)
Out/back split (derived)fixed at 40/60 (from the 200/300 source); flattening to 50/50 loses M3’s exit-fast/enter-slow rhythma more extreme split makes the out-leg read as yanking and the back-leg as slamming — stay near 40/60

Working ranges: duration 400–600ms, stagger 30–90ms (demo values, no official figure), n ≤ 12; total grows linearly with n — watch the duration + (n−1) × stagger ceiling.

When to use 3
  • Low-frequency re-skins on dashboards / component showcases: card-by-card re-dressing makes each module's change legible; spread = stagger × (n − 1), same structure as stagger-orchestration
  • A moderate card count (6–12) with simple per-card content (swatch + short label) — the 90° edge flashes past, so dense content would be unreadable mid-flip
  • Demo pages, component-library docs and design-system marketing pages that want the per-module re-dressing rhythm spelled out
When not to use 4
  • High-frequency theme toggling (Apple HIG: avoid motion on frequent interactions, research §5) — every click is a chain of n animations
  • Complex cards or imagery: at the 90° edge only a line remains — dense content turns unreadable mid-flip
  • Large n without a reduced stagger: total = duration + (n − 1) × stagger grows linearly and the last card visibly waits
  • Dozens of cards flipping at once: each 3D card takes its own compositing layer and the cost climbs with n (demo uses n=6)
Accessibility

The flip is interaction-triggered motion under WCAG 2.3.3 Animation from Interactions and must be disableable: the demo treats duration as 0 under prefers-reduced-motion, flipping faces instantly on click (sufficient techniques C39/SCR40, research §5); the theme state is carried by color as well — motion is never the sole channel for 're-skinned'; card text contrast is checked at 4.5:1 under both palettes (WCAG 1.4.3); re-clicking mid-animation neither hangs nor halts halfway (interruption = the old run jumps to its end, matching Chrome's 'a new transition skips the old one to its end', research §1.1/20a§S8).

Browser support

rotateY 3D transforms + perspective work in every engine; no View Transitions API and no clip-path needed — pure CSS keyframes + JS orchestration; with JS disabled the cards keep their current face (the toggle dies, a demo-control dependency). The face swap hangs on animationend, immune to setTimeout throttling.

Fallback

prefers-reduced-motion: reduce → duration treated as 0; a click flips every card's face instantly, no rotation (WCAG 2.3.3/C39, research §5); legacy environments without CSS animation → cards recolor directly; re-click mid-animation → every card lands flat instantly at the pre-click theme (= the old run's end state), then staggers toward the new target — never stuck halfway; the theme outcome is carried by color too, so it survives motion being disabled.
