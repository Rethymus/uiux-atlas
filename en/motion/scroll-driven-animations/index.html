Scroll-driven Animations

滚动驱动动画 · animation-timeline · scroll()/view()

animation-timeline: scroll()/view() hands animation progress to scroll position or an element's visibility progress: reading progress bars, reveals and parallax layers can run off the main thread (Chrome's official guide).

Web Standard ★★★
Live demo official default
Parameters
Motion▾
timelineview()

Timeline type: scroll() uses the scroll container's scroll progress (0–100%) as the timeline — the textbook case for progress bars/parallax; view() uses the element's own visibility progress inside the scroll container (IntersectionObserver-like) — the reveal card's choice. Note: named ranges like entry/exit/contain are defined only for view progress timelines (MDN animation-range); the demo substitutes cover full-range under scroll() and says so.

rangeStartentry 25%

animation-range start: a named range + offset percentage pair (official tiers cover/entry/exit/contain, Chrome guide & MDN, research 04 §4). Default entry 25% = the Chrome docs' Reveal example start: the animation begins once the element is 25% into entering the viewport.

rangeEndcover 50%

animation-range end. Default cover 50% = the official Reveal example end: the animation completes when the element has covered 50% of the viewport. Combinations with the end before the start behave inconsistently across implementations — avoid them. Range visualization: goo.gle/view-timeline-range-tool (research 04 §4).

Code breakdown

Structure & DOM

The demo is an inner scroll container with three pieces: a sticky reading progress bar (fixed to scroll()), a mid-page reveal card (driven by the params), and tall filler content above and below. DOM:

<div class="sd-scroller" tabindex="0">        <!-- overflow-y: auto; the nearest scroll container -->
  <div class="sd-progress"><div class="sd-bar"></div></div>  <!-- sticky top bar -->
  <p class="sd-spacer">…tall filler…</p>
  <div class="sd-card">Reveal card</div>       <!-- the timeline/range params land here -->
  <p class="sd-spacer">…tall filler…</p>
</div>

Key points:

  • scroll() resolves to the nearest scrolling ancestor (.sd-scroller); the bar sticks to its top and fills across the whole scroll;
  • view() uses the card’s own visibility progress within the scroll port — two timelines coexisting in one container, each minding its own subject;
  • The card is a plain in-flow element with no JS listeners attached — the whole point of declarative scroll-driven animations (replacing hand-written scroll-event logic, able to run off the main thread, research 04 §4).

Styling & Parameters

All three parameters are injected through --sd-* CSS variables:

/* Progress bar: fixed to scroll(), per the official example (scaleX, not width — compositor-friendly) */
.sd-bar {
  transform: scaleX(0);
  transform-origin: 0 50%;
  animation: sd-grow linear both;
  animation-timeline: scroll();   /* nearest scroll container */
  animation-duration: auto;
}
/* Reveal card: the timeline/range parameters take effect here */
@supports (animation-timeline: view()) {
  .sd-card {
    animation: sd-reveal linear both;
    animation-duration: auto;
    animation-timeline: var(--sd-timeline);   /* scroll() / view() */
    animation-range: var(--sd-range-start) var(--sd-range-end);
  }
}
@keyframes sd-reveal {
  from { opacity: 0; transform: translateY(28px); }
  to   { opacity: 1; transform: none; }
}

Where the numbers come from: the default entry 25% cover 50% is lifted verbatim from Chrome’s official Reveal example (research 04 §4: the animation starts when the image is 25% into entering the viewport and completes at 50% coverage); the scaleX(0→1) progress bar is likewise the official example’s recipe; animation-timeline must be declared after the animation shorthand (it is not part of the shorthand, research 04 §4). The named-range tiers (cover/entry/exit/contain + offset percentages) are specified in MDN’s animation-range — and entry/exit/contain are defined only for view progress timelines, so the demo substitutes full-range cover under scroll() and states that substitution in the UI.

Motion & Interaction

  • Progress bar: runs 0→100% with the container’s scroll — the official textbook case; static on unsupported browsers;
  • Reveal card: switching timeline between view()/scroll() instantly changes what “progress” means — view() watches the card’s own visibility, scroll() watches the container’s overall scroll; changing the range tiers re-maps the animation in place (scroll position untouched);
  • scroll() substitution: entry/exit tiers are swapped for cover 0%→100% full range, and the readout shows both the effective values and why; contain is likewise view-only and substituted too;
  • Keyboard & buttons: the scroll container is focusable with arrow-key scrolling; “Scroll to card / Back to top” buttons call scrollTo (with auto behavior under reduced-motion);
  • Dual degradation: without @supports the card is statically visible; under prefers-reduced-motion: reduce the reveal is disabled (always visible) while the progress bar remains (an informational map of scroll position, not decoration).

Parameter Sensitivity

ParameterTurning it up…Turning it down…
timelinescroll(): progress = the container’s overall scroll ratio; the card’s timing ties to total scroll distance, and entry/exit go inertview(): progress = the card’s own pass through the scroll port; range semantics wrap the element’s geometry — the default, official reveal scenario
rangeStartlarger entry percentages start the animation later (the element must be further in); contain starts once fully containedentry 0% starts as soon as the element pokes in; cover 0% = the timeline’s very start (measured from the container top)
rangeEndlarger cover/exit percentages finish later (cover 100% waits until the element scrolls fully past the viewport)cover 50% = the official default, completing at mid-pass; ends before the start behave inconsistently across implementations — avoid
Combined rhythmlate start + late end = a long, deep-scroll reveal; suits large imagery and tall cardsearly start + early end = a snap-in reveal; suits small cards

Working ranges: reveals commonly start at entry 10%–30% and finish around cover 40%–60% (the official example’s 25%/50% sits mid-range); progress bars stay on full cover (scroll()‘s cover is the entire timeline). Content first: anything a reveal can hide must have both fallbacks in place before shipping.

When to use 4
  • Reading progress bars: top bar scaleX (the scroll() official example, research 04 §4) — transform rides the compositor
  • Revealing images/cards as they enter the viewport (view() + animation-range; official example entry 25% cover 50%)
  • Parallax layers: foreground/background on different timelines/ranges (an official use case, research 04 §4)
  • Replacing hand-rolled scroll-event + IntersectionObserver progress logic — declarative and able to run off the main thread (research 04 §4)
When not to use 4
  • Pairing entry/exit ranges with a scroll() timeline — those named ranges are defined only for view progress timelines (MDN)
  • Putting content-hiding reveals on key information — users on unsupported browsers or reduced-motion must still read the content
  • Inlining animation-timeline inside the animation shorthand — the property is not part of the shorthand and must be declared after it (research 04 §4)
  • Driving the progress bar with width — use transform: scaleX to stay on the compositor (the official example's approach, research 04 §4)
Accessibility

Scroll-driven animations are locked to scroll position rather than playing over time, so vestibular load is lower than time-based animation; but content-hiding reveals must degrade twice: always visible under reduced-motion and always visible when unsupported (a reveal unveiling content ≠ content existing only through animation); the progress bar stays — it is an informational map of scroll position; keyboard users can Tab-focus the scroll area and scroll with arrow keys (supported in the demo).

Browser support

animation-timeline: Chrome/Edge 115+, Firefox 159+, Safari 26 (mdn/browser-compat-data measured 2026-11, research 02 §D6); the Chrome guide snapshot (research 04 §4) only confirmed Chrome/Edge 115+, with Firefox/Safari status per research 02's BCD data. MDN marks animation-range as Limited availability (not Baseline). The demo feature-detects with @supports and falls back statically. · Limited availability (Chrome 115+ / Firefox 159+ / Safari 26; not yet Baseline)

Fallback

When @supports (animation-timeline: view()) fails, the card is simply visible and the progress bar static — content is never hidden by the animation; under reduced-motion the reveal is disabled (always visible) while the progress bar stays: it reflects scroll position and is information, not decoration. Under scroll(), entry/exit ranges are explicitly substituted with full-range cover (see the timeline param).
