Scroll Snap

滚动吸附 · scroll snap · CSS Scroll Snap · 吸附滚动

Let snap positions take over scrolling: the container's scroll-snap-type picks axis and strictness, items' scroll-snap-align picks the alignment, scroll-padding/scroll-margin shape the snapport and snap areas — carousels and pagination handed back to native scrolling.

Web Standard ★★★
Live demo official default
Parameters
Motion▾
strictnessmandatory

Snap strictness, a CSS-type param (scroll-snap-type: x var(--snap-strict)). MDN's warning: mandatory can make content unreachable when it overflows — use it only when the amount of visible content is known; proximity lets the browser decide the snapping distance for general use. The demo's content is known, hence mandatory (research 10 §8.2 + 12 §4).

alignstart

The alignment point, a CSS-type param (scroll-snap-align: var(--snap-align)). start/center/end declares which edge of the snap area aligns with the snapport, per-axis overridable (12 §4); the demo defaults to start (same as the 12 §4 snippet).

stopalways

Per-item stops, a CSS-type param (scroll-snap-stop: var(--snap-stop)). The CSS default is normal (a fast flick may skip several snap points); both research snippets (research 10 §8.2, 12 §4) use always — "one card per swipe" — the carousel choice that prevents page-skipping.

Geometry▾
padding16px
px

scroll-padding-inline, a CSS-type param (container-side snapport inset). Default 16px from the 12 §4 snippet (scroll-padding-inline: 16px); the carousel convention in research 10 §8.4 uses 24px. Mandatory under sticky headers to leave room for them (12 §4). The item-side counterpart is scroll-margin (per-item fine-tuning, see the MDX).

Code breakdown

Structure & DOM

Snap scrolling is a two-layer structure — one scroll container plus a set of snap children — with all the semantics in CSS and zero JS:

<div class="rail" tabindex="0">      <!-- container: overflow-x auto + scroll-snap-type -->
  <div class="card">…</div>          <!-- items: scroll-snap-align / scroll-snap-stop -->
  <div class="card">…</div>
</div>

Key points:

  • The core concept (MDN): items expanded by scroll-margin become snap areas, the container inset by scroll-padding becomes the snapport, and “snapping” means aligning the two (12 §4);
  • scroll-padding lives on the container (mandatory under sticky headers, to reserve the header’s space), scroll-margin lives on items (per-item fine-tuning) — different jobs, do not conflate them;
  • The container also carries overscroll-behavior-x: contain so a swipe at the edge does not chain the whole page (the same rule as the scroll-overflow entry);
  • The rail keeps native scrolling: arrow keys work once focused, and snapping never changes scroll-event semantics.

Styling & Parameters

All four parameters are CSS-type, injected onto container/items via variables:

.rail {
  display: flex;
  gap: 16px;                                  /* same 16px gap as the 12 §4 snippet */
  overflow-x: auto;
  scroll-snap-type: x mandatory;              /* ← axis × strictness (mandatory/proximity) */
  scroll-padding-inline: 16px;                /* ← padding: insets the snapport */
  overscroll-behavior-x: contain;
}
.card {
  scroll-snap-align: start;                   /* ← align: start/center/end, per-axis overridable */
  scroll-snap-stop: always;                   /* ← stop: always forbids skipping cards (CSS default normal) */
}

Where the numbers come from:

  • gap 16px / scroll-padding-inline 16px / align start / stop always are taken item-by-item from the official concepts snippet in 12 §4; the carousel convention in research 10 §8.4 uses scroll-padding: 0 24px + x proximity — both are first-hand sources, pick per need;
  • mandatory’s precondition (MDN verbatim): use mandatory only when “the amount of visible content is known”; with overflowing content the user may never reach some of it — proximity for general use (research 10 §8.2);
  • The Level 2 scrollsnapchange / scrollsnapchanging events and SnapEvent (snapTargetBlock/snapTargetInline) are newer; MDN suggests @supports/fallbacks (12 §4) — the demo feature-detects and approximates the snapped card from scroll position otherwise.

Motion & Interaction

  • Snapping is the motion: the browser owns the docking, so snap positioning rides native scrolling — no hand-rolled easing, no dropped frames, identical behavior for touch/wheel/keyboard. That is the core argument for handing carousels back to native scrolling;
  • stop: always vs normal: always stops one card per gesture (the carousel standard); normal lets a fast flick skip several snap points (faster browsing in long lists) — choose by content density;
  • Programmatic paging: prev/next buttons scrollBy one step of “card width + gap”; under reduced-motion they use behavior: auto;
  • Snapped-card readout: listen to scrollsnapchange when Level 2 events exist, otherwise approximate from scroll position with rAF; the readout is announced through a polite aria-live region;
  • For the physics of release inertia and “how far a flick travels”, see the inertia-gesture entry; for scroll-progress-driven animation see scroll-driven-animations.

Real-world examples

  • MDN’s official snap concepts page: the direct source of this entry — the full container/item/snap-area/snapport concept set and examples come from that page (first-hand source in research 10 §8.2 and 12 §4);
  • The iOS home screen and system horizontal card streams: “one swipe, one stop” mandatory paging is the system-level prototype of this interaction (publicly known behavior, not frame-verified); the Web counterpart is mandatory + scroll-snap-stop: always;
  • Anchor positioning under sticky headers on docs sites: MDN explicitly documents scroll-padding for the “sticky header at the top” case (12 §4) — anchors landing on the heading instead of hiding beneath the header is scroll-padding’s most common production use.

Parameter Sensitivity

ParameterTurning it up…Turning it down…
strictnessproximity→mandatory: every scroll must dock, the strongest paging feel; with unknown content amounts it risks unreachable contentmandatory→proximity: only a gentle pull near snap points, long lists browse smoother; paging feel fades
aligncenter puts the “current card” mid-viewport (gallery focus framing); end suits right-aligned timelinesstart is the list/carousel default: cards align with the container edge, reading origin stays stable
stopalways: even fast flicks stop card by card, controlled pacing but slower in long listsnormal: flicks may skip several cards, efficient for long lists; carousels start “flying pages”
paddingmore snapport inset, more breathing room at rest; too much and the first/last cards may never reach alignmentthe breathing room vanishes and cards touch the edges; 0 restores raw snapping where sticky headers cover docked content

Rule of thumb: known content amount (carousels/sections) → mandatory + always + align start; unknown amounts (feeds) → proximity + normal; sticky headers always pair with scroll-padding; the container always carries overscroll-behavior: contain.

When to use 3
  • Horizontal card carousels/galleries — "one card per swipe" with scroll-snap-stop: always (12 §4)
  • Full-page vertical section storytelling, with mandatory when the visible content amount is known
  • Anchor positioning under sticky headers — scroll-padding reserves the header's space (12 §4)
When not to use 3
  • mandatory on scrollers with overflowing content — MDN: some content may become unreachable; proximity for general use (research 10 §8.2)
  • Feeds that want long inertial glides — snapping yanks every swipe back to a stop and breaks browsing rhythm
  • Treating snapping as the only spatial cue — snap points carry no semantics; keep visual progress or SR text for pagination
Accessibility

The rail keeps native scrolling (arrow keys once focused), with prev/next buttons as the reachable equivalent path; the snapped card is announced via a polite aria-live region; mandatory's unreachable-content risk hits keyboard users too — choose proximity when content amount is unknown; under reduced-motion programmatic scrolls use behavior: auto.

Browser support

Level 1 (type/align/stop/padding/margin) is widely supported in modern browsers; the Level 2 scrollsnapchange/scrollsnapchanging events and SnapEvent are newer — MDN suggests @supports/feature detection (12 §4). The demo detects the events and falls back to approximating the snapped card from scroll position. · Widely available

Fallback

Without scroll snap the rail degrades to a plain scrollable track (function survives, just no snapping); scroll-snap-stop and Level 2 events degrade silently when absent; without overscroll-behavior-x: contain (older iOS Safari) horizontal swipes may chain out of the page — see the scroll-overflow entry.

Sources 2
