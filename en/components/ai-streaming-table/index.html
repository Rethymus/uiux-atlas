AI Streaming Table

流式表格 · Streaming Table · GFM 表格流 · 渐进表格

Tables that grow with the token stream: row-level results of block memoization, fixed skeletons locking column widths, in-table scrolling that never breaks the session lock — wide tables stream too, without layout jumps.

tableLayoutfixed-skeleton

table-layout: fixed with per-column min-width/percentage widths: column widths never jump as rows grow (under auto, each new row re-fits widths and the whole table lurches); fixed is the streaming default, auto reserved for final polish (paired with autoLayoutOnComplete). An implementation suggestion with no official spec — unverified. Research 15 §5.2.

Switch to table-layout: auto after the stream ends (a content-fitted final pass); pair with a transition so the re-layout is visible and predictable — the layout was stable mid-stream, and the closing pass must not feel like a glitch. The off tier stays fixed throughout, the most stable. An implementation suggestion — unverified. Research 15 §5.2.

emptyCellPlaceholdershimmer

Placeholder for not-yet-arrived cells: a shimmer skeleton says "data is coming", a quiet "—" keeps table semantics (no data, no decoration). An implementation suggestion — unverified. Research 15 §5.2.

Skeleton row count mid-stream: the header renders first to lock widths, data-not-yet-arrived rows hold shimmer placeholders (assistant-ui's Mermaid pattern — skeleton while streaming, parse when complete — migrated to tables). Row-level fade-in interval: rows append one by one as the stream grows (a table is a block, rows its sub-structure), and per-row fades make the growth visible; 0 renders directly with no animation. Row-level progressive rendering is not separately documented (a natural consequence of block memoization) — no numeric convention is official. Research 15 §5.1/§5.2.

Code breakdown

Structure & DOM

A streaming table is “a block that grows”: the header (rendered first, locking widths) → data rows (appended with the stream, fading in per row) → skeleton rows (placeholders for data not yet arrived). The table as a whole is a markdown block; rows are its sub-structure.

<div class="tbl-scroll" tabindex="0">      <!-- in-table scrolling: never breaks the session lock -->
  <table style="table-layout: fixed">      <!-- fixed skeleton locks widths -->
    <caption class="sr-only">Quarterly metrics</caption>
    <thead><tr><th>Metric</th><th>Q3</th></tr></thead>  <!-- first render locks widths -->
    <tbody>
      <tr>Arrived row (block-memoized, never re-rendered)</tr>
      <tr class="skeleton" aria-hidden="true"><td>▒▒▒</td></tr> <!-- shimmer placeholder -->
    </tbody>
  </table>
</div>

Key points:

  • A table is a block, rows its sub-structure — Streamdown/remark-gfm supports GFM tables natively, and the table joins block-level memoization: finished row blocks never re-render mid-stream (official memoization docs cover block granularity only; row-level progressive rendering is not separately specified — a natural consequence of the block mechanism);
  • The header renders first to lock widths — fixed-layout column declarations hang on the header, so widths are decided before data arrives and row growth never shifts them;
  • Remend completion of unclosed tables is not listed in the termination docs (unverified whether it is handled specially) — a mid-stream half-table can stop at any row, and the renderer must self-stabilize with a “header fixed + rows completed as needed” strategy;
  • Division of labor with AI Streaming Response: prose blocks go to the streaming renderer, table blocks to this entry; the relation to the table entry: a full interactive table’s first-class abilities (sort/density/fixed columns) belong to the completed state — while streaming, only “grow + stay stable” are in scope.

Styling & Parameters

Six parameters map to three kinds of declarations: layout (fixed/auto), growth (skeleton count + row fade), and the container (in-table scrolling + closing strategy + cell placeholder):

/* Fixed skeleton: widths hang on the header, never moved by row growth */
.stream-tbl { table-layout: fixed; width: 100%; border-collapse: collapse; }
.stream-tbl th:first-child { width: 38%; }  /* column declarations live on the header */
.stream-tbl th, .stream-tbl td {
  border-bottom: 1px solid var(--border);
  padding: 6px 10px;
  font-size: 12.5px;
  text-align: left;
}
.stream-tbl td.num { text-align: right; font-variant-numeric: tabular-nums; }
/* In-table scrolling: past the threshold the body overflows, never breaking the session lock */
.tbl-scroll {
  max-height: var(--stm-max-h, 260px);
  overflow: auto;
  scrollbar-width: thin;
}
.stream-tbl thead th { position: sticky; top: 0; background: var(--bg-elev); }
/* Row-level fade: each arrival becomes visible in turn (duration via the CSS variable) */
.stream-tbl tbody tr { animation: stm-row var(--stm-row-ms, 250ms) ease both; }
@keyframes stm-row { from { opacity: 0; } to { opacity: 1; } }
/* Skeleton cells: a shimmering placeholder at real row height */
.stm-skel td {
  background: linear-gradient(90deg, transparent 30%, color-mix(in srgb, var(--text-1) 8%, transparent) 50%, transparent 70%);
  background-size: 200% 100%;
  animation: stm-sweep 1.4s linear infinite;
}
@keyframes stm-sweep { from { background-position: 100% 0; } to { background-position: -100% 0; } }

Where the numbers come from (official first-hand + unverified honestly labeled, research 15 §5):

  • Block-level memo: the officially documented memo granularity is the block (streamdown.ai/docs/memoization); row-level progression is a natural consequence, not separately specified;
  • Row fade / skeleton count are unverified — implementation suggestions, industry-common practice (this site’s defaults: 250ms / 3 rows);
  • The Mermaid analogy: assistant-ui’s official skill states “show a skeleton while streaming, parse only when complete” — the official neighboring basis for the skeleton-table migration;
  • Sticky header / in-table scrolling: native CSS capabilities; the numeric tiers are this site’s suggestions.

Motion & Interaction

  • Growth order: the header renders immediately → skeleton rows hold the space (skeletonRows) → data rows arrive one by one, each replacing a skeleton and fading in (rowRevealMs) → leftover skeletons exit when the stream ends;
  • Width stability: the fixed-skeleton tier stays fixed throughout; autoLayoutOnComplete: on switches to auto in a single pass after the stream ends (table-layout itself cannot animate — the re-layout lands the moment the stream closes; the research’s transition suggestion only applies at the column-width layer);
  • In-table scrolling: past maxBodyHeight rows the body goes overflow-auto, never competing with the session’s sticky-bottom for scroll; the sticky header keeps column heads visible while scrolling vertically;
  • Cell placeholders: not-yet-arrived cells hold shimmer skeletons or a quiet ”—”, always at real row height — completion swaps in with zero shift;
  • prefers-reduced-motion: stop the row fades and sweeps; rows render directly and skeletons freeze (demo behavior).

Real-world examples

  • Streamdown memoization docs: block-level memoization keeps finished blocks from re-rendering in streaming markdown — tables benefit as blocks, with GFM tables natively supported by remark-gfm (official docs, research 15 §5.1);
  • Streamdown termination docs: the termination list has no table entry — completion of unclosed tables is unverified territory and implementations must self-fallback (an official-doc absence reported honestly, research 15 §5.1);
  • assistant-ui Mermaid skill: the official skill states “show a skeleton while streaming, parse only when complete” — the isomorphic basis for the skeleton-table migration (research 15 §5.1);
  • This site’s table entry: Ant Table’s three density tiers, sticky header and virtual scrolling are the first-class abilities waiting in the completed state.

Working ranges: fixed throughout, 3 same-height skeletons, 250ms row fades, 260px in-table scrolling; the completed table’s interactive abilities (sort/density) never belong to the streaming phase.

When to use 3
  • Comparison/data tables streamed inside answers — the most common structured block in long LLM answers (GFM tables natively supported)
  • Generated reports with unpredictable row counts — rows append with the stream while fixed skeletons pin the widths
  • Wide tables inside a sticky-bottom session viewport — in-table scrolling never competes with the outer lock
When not to use 4
  • Streaming a table in auto layout — every arriving row re-fits widths and the whole table lurches (why fixed skeleton is the default)
  • Letting a long table break the session's sticky-bottom viewport — past the threshold the table must scroll internally, or streaming growth pushes the answer out of view
  • Re-rendering the whole table per row (dropping block memo) — Streamdown memoizes per block; finished row blocks never re-render for free, don't throw that away
  • Making skeleton row heights differ from real ones — zero-shift completion is the floor; unequal heights are a layout jump
Accessibility

Use real table semantics (th/scope/caption), mark the table aria-busy while streaming, and announce rows N/M arrived via an aria-live="polite" status line; skeleton rows are aria-hidden (screen readers skip decorative placeholders) and data rows enter the accessibility tree only on arrival; the in-table scroll region is keyboard-scrollable (tabIndex=0 + arrow keys) and the sticky header keeps column heads in view during horizontal scrolls; numeric columns right-align with tabular-nums (same rules as the site's table entry); prefers-reduced-motion drops row fades and renders directly.

Browser support

Demo infrastructure: table-layout and overflow-auto are native; row fades are CSS animation; sticky headers (position: sticky) are Baseline-supported everywhere. No new dependencies.

Fallback

Without CSS animation rows render directly (no fade, no information loss); without shimmer skeletons placeholders degrade to "—" or blanks; if in-table scrolling fails the table grows the page naturally (a plain long table) and the session layer still owns sticky-bottom.
