Generative UI

生成式 UI · Generative UI · 工具调用卡片 · Schema 驱动渲染

Model output → host component mapping: seven-state tool badges, schema-driven trees, progressive mid-stream rendering — the model can only request UI; rendering power always stays with the allowlist.

Code breakdown

Structure & DOM

Generative UI is a one-way pipeline of “model requests → host renders”: a tool card (collapsible) is the container, the tool header (name + state badge) is the state surface, and the Parameters / Result regions are the data surface.

<div class="tool">                                   <!-- Collapsible -->
  <button class="tool-head" aria-expanded="true" aria-controls="tool-body">
    <code>get_weather</code>                          <!-- tool name -->
    <span class="badge">◔ Running</span>              <!-- seven-state textual badge -->
  </button>
  <div id="tool-body" role="region">
    <p class="label">Parameters</p>
    <pre>{ "city": "Shanghai" }</pre>                 <!-- CodeBlock, streams in -->
    <p class="label">Result</p>
    <div class="weather-card">…</div>                 <!-- mapped component or JSON fallback -->
  </div>
</div>

Key points:

  • Dispatch rule (AI SDK official): the client dispatches on part.type === 'tool-${toolName}' within message.parts; the three intermediates are input-available (show “Loading weather…”) → output-available (spread part.output into the target component) → output-error (show part.errorText);
  • Seven-state vocabulary (Chat SDK tool.tsx, the most complete public intermediate-state word list): input-streaming = Pending ○, input-available = Running 🕐, output-available = Completed ✔, output-denied = Denied ✕, output-error = Error ✕, approval-requested = Awaiting Approval 🕐, approval-responded = Responded ✔;
  • The allowlist is the only boundary: assistant-ui’s official semantics — a spec referencing any component name outside the allowlist throws a type error instead of rendering; the AI SDK and assistant-ui routes agree: the model can only “request” UI; rendering power always stays with the host;
  • Relationship to the card: the mapped output (a weather card, etc.) is an ordinary card — the generative-UI delta is only “who decides to render it”: the host, via the allowlist, never the model.

Styling & Parameters

Six parameters cover mode, badges, collapsing and degradation:

/* Tool-body collapse: grid-template-rows 0fr/1fr height transition */
.tool-body { display: grid; grid-template-rows: 0fr; transition: grid-template-rows 0.25s ease; }
.tool-body[data-open="true"] { grid-template-rows: 1fr; }
/* Seven-state badges: text first, color redundant */
.badge[data-tone="running"] { color: var(--accent); }
.badge[data-tone="error"]   { color: #ff4d4f; }
.badge[data-pulse="true"]   { animation: pulse 1.2s ease-in-out infinite; }

Where the numbers come from (research 15 §2):

  • The 7-state badge vocabulary is verbatim from Chat SDK components/ai-elements/tool.tsx (Pending/Running/Completed/Denied/Error/Awaiting Approval/Responded); structure Tool (Collapsible) > ToolHeader (name + badge) > ToolContent > ToolInput (“Parameters” + CodeBlock) > ToolOutput (“Result”; objects → CodeBlock, strings → text, errors show errorText first);
  • Auto-collapse 1s comes from the same repo’s reasoning.tsx AUTO_CLOSE_DELAY = 1000ms (fires once), auto-expand while streaming and collapse when done;
  • Multi-step tool loops are capped by the official example stopWhen: isStepCount(5);
  • CopilotKit “Components as Tools” official semantics: a component ‘reads only its props and can stream in as the agent fills the payload’; naming tools with verbs (render_bar_chart) improves model hit rate;
  • Badge copy overrides (Pending→Running) and inputPreviewMs, approvalFlow etc. are parameterization suggestions from research §2.3; the demo adopts the strategies while all numbers stay officially documented.

Motion & Interaction

  • Props streaming in: the Parameters mono block grows character by character (the demo’s 28ms/char pace is a teaching value, unverified); in json-spec mode the spec prefix is scanned with a regex for closed fields — a value renders the moment it closes, reproducing assistant-ui’s “partially-streamed spec renders progressively” semantics;
  • Collapse timing: auto-expanded while streaming (state visibility first), auto-collapsed 1s after output-available/output-error, manually re-expandable; collapsing animates only grid-template-rows (a transitionable layout property) and height;
  • State badges: Pending/Running pulse at 1.2s (presence = “the system hasn’t crashed”, one of NN/g’s three values of progress indicators); done/error are static, with text always the first carrier;
  • Degradation path: unknown component name → JSON fallback card (allowlist on); the allowlist-off tier deliberately demonstrates the risk of mounting unregistered components;
  • prefers-reduced-motion: pulse and caret blinking are removed and the collapse switches instantly.

Real-world examples

  • AI SDK official example: a weather tool’s three-state card — input-available shows “Loading weather…”, output-available spreads the output into the weather component, output-error shows the errorText; multi-step loops capped with stopWhen: isStepCount(5) (official generative-user-interfaces docs);
  • Chat SDK (vercel/chatbot) Tool component: seven-state badges plus the ToolInput/ToolOutput split, error-first errorText and object results landing in a CodeBlock — a production anatomy of the tool card (verified against the repo’s components/ai-elements/tool.tsx);
  • CopilotKit “Components as Tools”: useComponent({ name, description, parameters: zodSchema, render }) registers a React component as a front-end tool, the zod schema doubling as the props schema, with props streaming in as the agent fills them; headless setups render tool calls via CopilotChatToolCallsView (official docs).

Parameter Sensitivity

genuiModejson-spec grants the model more composition freedom but widens the security audit surface (arbitrary JSON trees)tool-map is explicit one-to-one mapping with the smallest audit surface — and the least freedom

allowliston: unknown names degrade to a JSON card; rendering power stays with the host (the only safe form)off: unregistered components mount directly — fine for demos, in production it hands the XSS surface to the model
streamPropson: render-as-it-fills; first fields appear tens of ms earlier; the implementation must tolerate partial dataoff: props arrive whole — simpler, but tools with long arguments get a blank wait
resultRendercomponent-map is generative UI proper; raw-json equals the no-mapping official defaultraw-json always works (the degradation fallback) but is denser in syntax than in structure

Working ranges: seven badge states are enough (don’t invent an eighth); auto-collapse 1s; multi-step loops ≤5; the allowlist must be declared explicitly — “allow-all by default” is not a default, it’s a vulnerability.

When to use 3
  • Intermediate states and result cards for LLM tool calls: weather/stock/search structured outputs (AI SDK official paradigm)
  • Host renderers for model-composed UIs: JSON spec trees + component allowlist (assistant-ui GenerativeUISpec)
  • Human-in-the-loop approval flows: approval-requested / approval-responded states (Chat SDK vocabulary)
When not to use 4
  • eval/innerHTML-ing model JSON into the page — an injection highway; rendering must stay inside the allowlist (treat AI output as untrusted input)
  • A nominal allowlist that renders any name handed to it — assistant-ui's official semantics throw on unregistered names instead of rendering
  • Distinguishing intermediate states by color alone — Pending/Running/Completed need textual badges (unreadable for color-blind users)
  • Tool cards that never collapse — each one eats layout in a streamed session; collapse 1s after completion (Chat SDK AUTO_CLOSE_DELAY strategy)
Accessibility

The tool header is a button[aria-expanded][aria-controls] plus a content region (official Collapsible semantics); the seven-state badges must be readable as text, with color as redundant reinforcement only; announce state changes via aria-live="polite"; the mono Parameters/Result blocks are real text for screen readers, never screenshots; in-stream spec skeletons are decoration (aria-hidden) while completed fields carry the information; the error card's errorText uses role="alert".

Browser support

Pure DOM + CSS demo: the collapsible uses button[aria-expanded] + a grid-template-rows 0fr/1fr height transition (fully supported); JSON parsing and regex field extraction are basic JS. Production features (React Server Component streaming, zod schema validation) sit inside the current Baseline.

Fallback

Any parse failure or unknown component must land on the degradation render: unknown component name → JSON card (official semantics of the allowlist-on tier); partial spec → skeleton placeholder + progressive fill of completed fields (demo behavior); if JS fails the tool card degrades to a static collapsible and the badge copy remains the sole state carrier (never color alone).
