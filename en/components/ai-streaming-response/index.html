AI Streaming Response

AI 流式响应 · Streaming Markdown · 流式渲染 · 打字机流

Progressive rendering of AI answers: self-healing unclosed markdown, a trailing caret, sticky-bottom scrolling with user-interrupt, and two-level throttling — the layout stays stable wherever the token stream is.

Code breakdown

Structure & DOM

A streaming-response container is a “text-arrival state machine”: a scroll container (sticky bottom) → a role=“log” body (blocks appended one by one) → a trailing caret (pseudo-element). Three layers, three jobs, no overlap.

<div class="chat-scroll">              <!-- sticky-bottom scroll region -->
  <div class="stream-body" role="log"> <!-- body: blocks appended as they arrive -->
    <p>Finished block (never re-rendered)</p>
    <p>Growing block<span class="caret"></span></p>
  </div>
  <button class="jump">↓ Jump to bottom</button> <!-- only when !isAtBottom -->
</div>

Key points:

  • The caret is not a DOM node — Streamdown implements it as a CSS variable --streamdown-caret plus an ::after on the last child; remove the attribute when the stream ends and it disappears, zero extra nodes;
  • Unclosed syntax is the norm, not the exception: tokens can stop mid-way at **This is bol, an unterminated backtick, or [Click here, and the renderer must render them “as if closed” instead of erroring or flashing (Streamdown’s official problem statement);
  • Finished blocks must stay stable: Streamdown parses content into independent blocks with block-level memoization — only changed blocks re-render (in vercel/chatbot, MessageResponse = memo(Streamdown) whose comparator only checks whether children changed).

Division of labor with skeleton screens: skeletons cover “this block hasn’t arrived yet”, streaming rendering expresses “content is growing”; secondary regions like reasoning panels also do their own panel-internal sticky bottom (vercel/chatbot reasoning.tsx sets scrollTop = scrollHeight on every content change while streaming), decoupled from the outer conversation lock.

Styling & Parameters

Six parameters map to three kinds of declarations: the caret (a data attribute picks the glyph), the entrance animation (duration via a CSS variable), and behavior switches (JS-type, subscribed by the demo):

/* Caret: attached to the last child only while streaming */
.stream-body[data-live="true"] > :last-child::after {
  content: var(--srd-caret-char, "▋");       /* block=▋ / circle=● */
  color: var(--accent);
  animation: blink 0.9s steps(1) infinite;   /* blink period is this site's suggested 800–1000ms */
}
/* Per-token entrance: official default 150ms + ease + fill-mode both (hide-then-show, no flash) */
.stream-body[data-anim="fadeIn"] .tok { animation: fade var(--srd-anim-ms) ease both; }

@keyframes fade { from { opacity: 0; } }
@keyframes blink { 50% { opacity: 0; } }

Where the numbers come from (all officially documented, research 15 §1):

  • Caret shapes: caret="block" (▋) | "circle" (●), shown only while isAnimating && streaming, officially recommended on the last assistant message only;
  • Entrance animation: three tiers fadeIn / blurIn / slideUp, default 150ms, easing ease, fill-mode both; fast models officially get blurIn + 200–300ms + ease-out;
  • Token pacing: AI SDK smoothStream delayInMs defaults to 10ms (skipped when the document is hidden so timer throttling can’t stall the stream); chunking defaults to 'word', and CJK explicitly calls for Intl.Segmenter (word chunking fails on Chinese/Japanese/Korean);
  • Client throttle: useChat exposes a throttle option, 50ms in the official example;
  • Sticky bottom: use-stick-to-bottom — “smart logic to distinguish user scroll from programmatic animation scroll, without debouncing that could miss events”; scrollToBottom() returns Promise<boolean>;
  • “rAF frame merging” is a community implementation device — not an official term (unverified); the official two-level plan is smoothStream (server) + throttle (client).

Motion & Interaction

  • Token pacing: the demo ticks per token at smoothDelayMs (default 10ms), emulating smoothStream’s server-side rhythm; delayInMs: null or 0 means no throttle. Background tabs clamp timers anyway — the official answer is “skip the delay when the document is hidden”, not fighting throttling;
  • Interrupting sticky bottom: a wheel-up or a scrollbar drag that leaves the bottom releases the pin on the same frame, no debounce (missing one event means the user can never catch up; NN/g: a scroll that outruns the user must be stoppable); the jump-to-bottom button appears only when !isAtBottom and re-pins on click;
  • Entrance animation: animates only opacity / filter / translate; animation-fill-mode: both gives hide-then-show so batched tokens never flash; pre/svg/math are skipped (inline code does animate — official behavior);
  • Caret lifecycle: attach data-live="true" when the stream starts, remove it when it ends — the caret is the state machine (“is it generating” compressed into one pseudo-element);
  • Honest mode: unclosedRepair: off shows raw token syntax for teaching/debugging; production defaults to on;
  • prefers-reduced-motion: drop the entrance animation and caret blinking (demo behavior); streaming itself continues.

Real-world examples

  • Vercel Chat SDK (vercel/chatbot): components/ai-elements/message.tsx ships MessageResponse = memo(Streamdown) with the comparator prevProps.children === nextProps.children (no re-render when the text is unchanged) and the plugin set {cjk, code, math, mermaid} — the first-hand production sample of Streamdown (verified against the repository, research 15 §1.1);
  • assistant-ui dual paths: StreamdownTextPrimitive defaults to mode="streaming" — finished blocks stay stable, only the last block grows; the lightweight MarkdownTextPrimitive has smooth on by default (smoothed token emission), and large messages can enable defer so React prioritizes input and scrolling — but defer must stay constant across mounts (official skill docs);
  • use-stick-to-bottom (by Sam Denty, “Designed with AI chat bots in mind”): adopted directly by vercel/chatbot’s Conversation; a ResizeObserver watches content size changes, and its spring scroll beats fixed-length easing (fixed easing desynchronizes while streamed content keeps resizing) — the reference implementation for sticky bottom and interrupt (official README).

Parameter Sensitivity

ParameterTurning it up…Turning it down…
caretTypeblock reads terminal-like and stays visible across long answerscircle is subtler for dense layouts; none loses the “generating” signal, leaving shimmer as the only cue
animStyleblurIn is the richest and noisiest — officially reserved for fast models; slideUp has strong motion directionfadeIn is the quietest; off costs nothing and is safest for screen readers and low-end devices
animDurationMspast 200ms on a fast model the animation lags behind tokens and backlog piles up (official cap 300)under 100ms it is nearly no animation and flash risk returns on batched arrivals (fill-mode both can’t save multi-mounts per frame)
smoothDelayMspast 30ms typing visibly slows and total time stretches; hidden tabs should skip the delay regardless (official behavior)0 streams at full speed, pushing all pressure onto the client throttle; the official 10ms is the compromise
unclosedRepairon (default): the mid-stream layout equals the final layout; closers swap in seamlesslyoff shows raw syntax with bare ** markers — a debugging tool that reads as “broken” in production
lockBottomon: the viewport follows new content and the reading flow never breaks; the cost is that interruption must workoff: new content grows silently out of view and readers discover they’ve fallen behind (the classic failure state)

Working ranges: pacing 10ms, entrance 150ms (blurIn 200–300ms on fast models), blink period 800–1000ms; the caret belongs only to the last message, and the two throttle levels each cover one stage (server pacing + client render frequency).

When to use 3
  • Assistant message bodies in LLM chat — the standard container for streaming markdown (Streamdown's official positioning)
  • Secondary sticky-bottom in reasoning panels: panel-internal auto-scroll decoupled from the outer conversation (vercel/chatbot reasoning.tsx)
  • Any rich text arriving token by token: report generation, code-completion streams, long summaries
When not to use 4
  • Showing the caret/entrance animation on historical messages — the caret is officially for the last assistant message only
  • Re-rendering the whole markdown tree per character — finished blocks must be memoized (Streamdown block-level memoization)
  • Debouncing user-scroll detection for sticky-bottom — use-stick-to-bottom explicitly rejects 'debouncing that could miss events'
  • Pacing tokens at 10ms timers in background tabs — smoothStream skips the delay when the document is hidden
Accessibility

Give the streaming region role="log" so screen readers can follow appended content, plus an aria-live="polite" status line announcing generating/done/stopped; per-token animation carries no semantics — never put key information only in the animation layer; the caret is pure decoration (::after); sticky-bottom must be user-interruptible (NN/g: animate on the real clock, and let users stop a scroll that outruns them); under prefers-reduced-motion drop entrance animation and caret blinking, keeping a static caret or none.

Browser support

Demo infrastructure: CSS animation and ::after carets are universally supported; JS word segmentation prefers Intl.Segmenter (Chrome 87+/Firefox 125+/Safari 14.1+, Baseline 2024) with a regex fallback; overflow scrolling is native. Production Streamdown adds Shiki highlighting (supported in all modern browsers).

Fallback

Without Intl.Segmenter, fall back to regex tokenization (CJK degrades to per-char, pacing stays smooth); animation and caret are progressive enhancements — streaming works without them; if the sticky-bottom JS fails, the container remains a normal scroll region, just without auto-follow.
