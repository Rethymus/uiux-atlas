## Structure & DOM

A curve handoff is "one lane + one draggable element" — the handoff is a **timing** concern, not a structural one:

```html
<div class="lane" role="button" tabindex="0">   <!-- Pointer event stream + keyboard equivalent -->
  <div class="marker" aria-hidden="true"></div> <!-- target position (pure decoration) -->
  <div class="puck"></div>                      <!-- dragged element: the only transform host -->
</div>
```

Key points:

- During the drag **no animation runs at all**: pointermove writes `transform` directly, tracking 1:1; the spring starts only at release — both segments share the same position and velocity state;
- Velocity comes from pointer sampling: each move records `(x, t)`, instantaneous velocity is smoothed with an EMA, and release yields the gesture velocity (px/s);
- `pointercancel` (incoming call, system gesture takeover) must be treated as a release so the spring takes over normally — the same Pointer stream as the inertia-gesture entry;
- Position always rides `translate3d` (compositor path); no layout is touched per frame.

## Styling & Parameters

All three parameters are JS-type, assembled straight into the integrator, no CSS variables:

```js
// Spring segment: semi-implicit Euler (same as the springSlot recipe in research 10 §2.2, m=1)
// m·x'' + c·x' + k·(x−target) = 0
v += (−k * x − c * v) * dt;   // dt clamped ≤ 1/30s against frame jumps
x += v * dt;
el.style.transform = `translate3d(${x}px, 0, 0)`;
// Rest: dual |v| and |x| thresholds (the restSpeed/restDelta idea; Motion's granular values 0.01/0.005, research 10 §2.2;
// the demo relaxes to 0.5/0.5 with an 8s fallback — demo values)
```

Where the numbers come from:

- `stiffness 300 / damping 25`: the springSlot code default in research 10 §2.2 — the §2.3 computed "medium, slight bounce" tier (**ζ≈0.722, overshoot≈3.8%, peak at 262ms**); ζ = c/(2√(k·m)) and overshoot % = e^(−πζ/√(1−ζ²))×100 are that page's Python-verified formulas;
- **The official semantics of the velocity handoff**: Motion — "physics-based spring animations incorporate the velocity of any existing gestures or animations", with `velocity` defaulting to "the current value's velocity"; the counterexample is duration-based springs "starting from rest and ignoring velocity" (research 10 §7.3, quoted verbatim); Apple concurs: SwiftUI docs state successive springs "**preserve velocity**" across handoffs (research 04 §1.3);
- Routing the release: injecting velocity into a spring is the recommended shake pattern (research 10 §4.2: give it initial velocity, not keyframes); drawers route first through thresholds — vaul's `VELOCITY_THRESHOLD 0.4` + `CLOSE_THRESHOLD 0.25` (released when velocity exceeds the threshold or progress passes 25%, research 10 §5.1);
- `FLICK_VELOCITY = 1500 px/s` (keyboard flick) and the velocity-smoothing factor: demo values, not official numbers.

## Motion & Interaction

- **Two segments, one line**: the tracking segment runs zero easing (easing decouples pointer from element); the spring resumes from "current value + current velocity" — spliced together they form one C¹-continuous curve with no perceptible joint;
- **The difference between a hard flick and a soft push lives entirely in the handoff**: a slow drag releases at ≈0 velocity and the spring settles quietly; a hard flick hands over a large velocity and the spring overshoots on inertia before damping catches it — overshoot is predictable from ζ and release velocity, and the demo shows both live;
- **The handoff=off contrast**: the same flick with velocity zeroed before start — the return "has no drive", dragged back rather than returning by itself; exactly the ailment of fixed-duration tweens taking over releases (the duration-based anti-pattern, research 10 §7.3);
- **Compute ζ before adopting a spring (research 10 §2.3 craft 3)**: velocity into an under-damped spring (ζ\<0.4) overshoots uncontrollably; the demo pins ζ and predicted overshoot to the readout — check it before tuning;
- **Interruptibility**: pressing again cancels the spring and re-enters tracking with a cleared velocity — interruption/re-trigger stay continuous, the other half of the handoff promise;
- **reduced-motion**: tracking is kept (direct manipulation is not decorative motion) and release lands directly without integration (same convention as the inertia-gesture entry);
- Performance: only transform is written throughout; the division of labor with inertia gliding — inertia has no arrival bounce and bounces only past bounds (handoff-curves and inertia-gesture are each other's counterpart).

Interlinks: slot-spring owns "spring feel and tiers" (the layoutId library version); damping-craft owns the full ζ feel map; smooth-craft carries the interruption-relay as one of its craft principles.

## Real-world examples

- **Motion's (framer-motion successor) spring engine**: the docs promise physics springs absorbing gesture velocity with `velocity` defaulting to the current value's velocity — "drag to track → release to spring" is one continuous curve inside the library (research 10 §7.3, first-hand motion.dev docs);
- **The vaul bottom sheet** (same author as sonner): release-velocity threshold 0.4 and progress 25% decide "let go or pull back", with the transition at transform 0.5s cubic-bezier(0.32, 0.72, 0, 1) — a complete open-source implementation of the velocity relay (research 10 §5.1, source verified verbatim);
- **SwiftUI spring relays**: the official documentation states that successive spring animations preserve velocity — the underlying guarantee of iOS system feel (list bounces, sheets) (research 04 §1.3, Apple docs JSON endpoint).

## Parameter Sensitivity

| Parameter | Turning it up… | Turning it down… |
| --- | --- | --- |
| `stiffness` | ω₀↑: a fiercer return, faster arrival; at the same ζ the overshoot ratio is unchanged (research 10 §6.3) | a sluggish return; very low k with high damping crawls back through mud |
| `damping` | ζ↑: fewer wobbles, exponentially shrinking overshoot; ζ=1 critical is the fastest no-overshoot reset | ζ↓: multi-bounce settling after flicks; ζ\<0.4 with high velocity loses control (craft 3) |
| `handoff` | on: hard flicks and soft pushes each get their own landing — "in hand" extends all the way to rest | off: every release looks the same — a demo-only anti-pattern, forbidden in production |

Rule of thumb: hand over position *and* velocity together; compute ζ first (keep the micro-bounce tier at 0.7±0.1) before deciding how much velocity to admit; route drawers through a velocity threshold before the spring (the vaul paradigm); never let a fixed-duration tween take over a release.
