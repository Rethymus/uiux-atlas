## 结构与 DOM

演示是一个**审批队列**:5 张待批卡片,点「批准」触发模拟的服务端确认,反馈策略由 `feedback` 参数切换:

```html
<div class="dt-item" data-state="working">
  <span class="dt-title">报销单 #A-1024 处理中…</span>
  <button class="dt-approve" disabled>批准</button>
</div>
<span class="dt-live" aria-live="polite"></span> <!-- 状态播报 -->
```

关键点:

- 三种策略共用同一延迟源(`delay` 参数):`wait` 按钮禁用+文案「处理中…」;`optimistic` 立即显示「✔ 已记录(后台确认中)」、延迟后翻「已批准」——两阶段结构,不是一蹴而就;`skeleton` 标题替换为微光骨架块;
- 面板实时显示完成数、上次耗时,并对 `delay≤400ms` 翻绿「Doherty 达标」;
- `aria-live="polite"` 隐形播报区把每个状态变化说给读屏。

## 样式与参数

```css
.demo-stage { --dt-delay: 700ms; } /* DemoStage 注入,demo 的 setTimeout 经 store 读值 */
.dt-skel {
  background: linear-gradient(90deg, … );
  background-size: 200% 100%;
  animation: dt-shimmer 1.1s linear infinite; /* reduced-motion 时取消 */
}
```

- `delay` 默认 **700ms**:刻意越过阈值让「等」被看见;Doherty & Thadani 1982 的标准是 \<400ms(此前行业标准 2000ms,lawsofux 原文);
- `feedback` 三档:`wait`(干等)/ `optimistic`(乐观更新)/ `skeleton`(骨架屏)——对应 07§27 的三条感知性能出口;
- 阈值判定 `delay ≤ 400` 只是演示口径;真实系统的 400ms 要从「用户操作 → 可感知反馈」全程计,含网络与渲染。

## 动效与交互

- 连点 5 张批准可体感「节奏」:≤400ms 时下一次点击几乎不用减速;700ms 时开始出现「等一下再点」的迟滞;1500ms+ 时用户会去点别的卡片——这正是 Doherty 关心的生产力损失;
- 骨架微光是 1.1s 线性循环的 `background-position` 动画(合成器友好的 gradient 位移动画);`prefers-reduced-motion: reduce` 时取消,骨架退化为静态灰块;
- 乐观更新阶段 1 用文本「✔ 已记录(后台确认中)」区分于最终「已批准」——乐观态必须可识别,失败路径才谈得上回滚(demo 恒成功,真实实现需处理失败撤销);
- 所有状态变化经 `aria-live` 播报,不依赖颜色。

## 真实产品案例

- **社交产品的点赞/收藏**:点赞立即 +1、红心立即点亮(乐观更新),后台静默确认——「可回滚操作乐观先行」已成各社交 App 事实标准(07§27 感知性能的泛化惯例,未见调研点名单一产品);
- **内容平台的骨架屏**:列表首屏先渲染灰块骨架、数据到位后填充——布局提前稳定、可交互感提前到来(07§27「感知性能」的通行实现);
- **NN/g 响应时间三限**:0.1s 内感觉「瞬时」、1s 内保持思路、10s 是注意力上限——与 Doherty 的 400ms 互补成完整的等待分层策略(0.1–1s 状态反馈、1–10s 进度指示)(调研 07§18/§27)。

## 参数敏感度

| 参数 | 调大会… | 调小会… |
| --- | --- | --- |
| `delay` | >1000ms 后干等策略几乎不可接受,连点节奏被彻底打断;2000ms 是 Doherty 之前的旧标准 | ≤400ms 徽章翻绿;0ms 直接完成——注意真实系统还要计入网络与渲染 |
| `feedback` | optimistic 让「感觉到的等待」趋近 0,但必须配失败回滚;适合可回滚操作 | wait 是基线对照组——把策略切回 wait 再对比,才能量出感知差异 |
| `skeleton` | 骨架让等待「有形」,布局提前稳定;>10s 的任务骨架不够,要上进度条(三限) | — |

经验结论:400ms 是**节奏**阈值(NN/g 三限是**分层**阈值,两者互补);前端能优化的是「等的感觉」,真正 >10s 的任务要给取消、给进度、给完成后的收尾(接峰终定律)。
