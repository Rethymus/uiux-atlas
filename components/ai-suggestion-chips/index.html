代码拆解

结构与 DOM

建议操作 chips 是「回答的路标层」:滚动容器(横向 ScrollArea)→ 建议按钮组(outline + sm)→ 点击接线(onClick → 发送)。三层各管一件事,路标属性压倒装饰属性。

<div class="chips" role="group" aria-label="建议追问 Suggested follow-ups">
  <button class="chip">对比流式渲染的两种节流策略</button>
  <button class="chip">给这个方案写验收要点</button>
  <button class="chip" aria-disabled="true">已发送 ✓…</button> <!-- postClickState -->
</div>

关键点:

  • 点击即发送是官方用法——AI Elements Suggestion 的 onClick 回调直接把 suggestion 字符串交给 sendMessage,没有「填充输入框」中间态(想要中间态要自行改写,并如实标注非官方);
  • 换牌钉在轮次边界——assistant-ui SuggestionAdapter 的 key 机制只在 run 结束后为该 key 重新生成建议,天然防抖;相邻官方机制是 AI SDK 状态机:流式期间不逐 token 刷新,等 status === ‘ready’;
  • 数量与截断无官方规范(未证实)——官方示例 3–8 条、实践 3–4 条;建议是路标,一排路标就成了路牌墙;
  • 与 AI 流式响应 的时序契约:chips 属于流结束后的层,流式期间牌面必须静止;与 AI 回答安全态 的衔接:追问建议同样要过链接安全闸。

样式与参数

六个参数对应三类声明:容量(数量/截断)、时机(换牌纪律)、点击生命周期(行为 + 后态 + 容器):

/* 单体 chip:官方 variant="outline" size="sm" 的按钮形态 */
.chip {
  border: 1px solid var(--border);
  border-radius: 999px;
  background: var(--bg-elev);
  color: var(--text-1);
  font: inherit; font-size: 12.5px;
  padding: 5px 14px;
  cursor: pointer;
  white-space: nowrap;            /* 截断由 max-width + ellipsis 承担 */
  max-width: 30ch;
  overflow: hidden;
  text-overflow: ellipsis;
}
.chip:hover { border-color: var(--accent); color: var(--accent); }
.chip:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
/* 已发送态:✓ 徽标 + 禁用——状态不只靠颜色承载 */
.chip[aria-disabled="true"] {
  border-style: dashed;
  color: var(--text-faint);
  cursor: default;
  pointer-events: none;
}
/* 官方 Suggestions 容器 = 横向 ScrollArea(可拖动滚动条) */
.chips-row {
  display: flex; gap: 8px;
  overflow-x: auto;
  scrollbar-width: thin;
  padding-bottom: 4px;
}

数值出处(官方一手 + 未证实如实标注,调研 15§4):

  • 单体形态:variant=“outline” size=“sm” 按钮(AI Elements Suggestion 一手源码);
  • 容器:横向 ScrollArea、可拖动滚动条(官方 Suggestions);
  • 数量上限:官方均未规定(未证实);官方示例 3–8 条(AI Elements demo 8、基础用法 3),实践 3–4;
  • 截断宽度:官方无规范(未证实);demo 取 24 字符档并挂 title 全文;
  • 点击后态:官方默认 = 立即发送,后态(mark-sent/disable/hide)为防连点的实践建议(未证实)。

动效与交互

  • 换牌纪律:demo 以一段模拟流演示两种策略——ready-gated 档流式期间牌面完全静止、流结束整组淡入换新;live-stream 档牌面随流抖动(教学用反面教材,生产禁用);
  • 点击即发送:所选 chip 立即进入已发送态(✓ 徽标 + aria-disabled),模拟消息追加进会话;fill-composer 档改为把文本填入下方输入框,等用户自己按发送(标注:自改写,非官方);
  • 防连点后态:mark-sent 保路标禁连点;disable 整组不可点;hide 整组移除——三者都保证「一次点击最多一次发送」;
  • 截断:超长建议按 chipMaxLength 截断 + 省略号,全文挂 title 与 aria-label,悬停可读、读屏可读;
  • 溢出:超出 maxChips 的建议仍在组内,靠横向滚动区承载(官方容器语义),键盘可聚焦到达。

真实产品案例

  • AI Elements Suggestion(vercel/chatbot suggestion.tsx):容器 Suggestions = 横向 ScrollArea;单体 = outline/sm 按钮,onClick 回调直接吐 suggestion 字符串接 sendMessage——「点击即发送」官方用法的第一手样本(仓库源码核对,调研 15§4.1);
  • assistant-ui SuggestionAdapter:createSuggestionAdapter 提供 key(变化的 key 触发为已结束的 run 重新生成建议)与 generate(Promise | AsyncGenerator,建议本身支持流式异步生成);官方定位「starter prompts, contextual actions, and guided composer options」——key 机制就是「换牌钉在轮次边界」的官方实现(调研 15§4.1);
  • AI SDK Chatbot 状态机:status: submitted → streaming → ready——建议刷新应等 ready,这是数量/防抖官方均未规定时最硬的相邻官方依据(调研 15§4.2);
  • CopilotKit:侧无独立 chips 组件规范(交互组件走 tool 渲染),其 chips 数量/防抖约定未证实——如实申报,不作为依据。

参数敏感度

参数调大会…调小会…
maxChips>6 路标变路牌墙,每条被点概率稀释(官方 demo 8 条属展示极限)1–2 条引导变独裁,用户没得选;3–4 是实践甜点
chipMaxLength>32 整行被一两条长建议占满,横向滚动变长跑<16 语义截断过度,悬停才能看清;24 字符档兼顾中文双倍宽
updatePolicylive-stream 牌面随流抖动,点不准、抢注意力(反面教材)ready-gated 流中静止、整组换新——唯一生产档
onClickBehaviorfill-composer 给编辑权但多一步,转化率降(非官方,需标注)send-immediate 官方默认,零中间态、一步到位
postClickStatehide 版面最干净但路标消失;mark-sent 保上下文都优于「无后态」——原样可点等于邀请重复发送
scrollDirectionwrap 折行撑高会话,挤占回答区horizontal 官方容器语义,行高恒定;键盘需可达

经验区间:3–4 条、24 字符截断、ready-gated 换牌、send-immediate + mark-sent 后态;建议层的一切交互都要回答「流结束时它在不在动」。

适用场景 3
  • 回答流结束(status === 'ready')后的追问引导——AI Elements Suggestion 的官方定位:starter prompts 与 contextual actions
  • 空会话的冷启动示例问题(官方基础用法 3 条)
  • 工具调用结果后的后续操作入口(如「导出这张表」「换个图表类型」)
何时不要用 4
  • 流式期间逐 token 刷新建议牌——应等 status === 'ready'(AI SDK 状态机),抖动抢注意力还点不准
  • 一排 8+ 条建议塞满整行——数量上限官方未规定,但建议是路标不是路牌墙(实践 3–4 条)
  • 点击后 chips 原样保留可再点——没有后态等于邀请重复发送(官方默认点击即发,连点即连发)
  • 把关键操作(如「删除全部」)做成建议 chip——建议会被整组换牌/移除,关键操作不能寄生在易变层
无障碍

chips 是真按钮(可聚焦、有按压态),横向滚动区要可键盘滚动(容器 tabIndex 或逐个 Tab 聚焦即可达);换牌瞬间整组内容变化用 aria-live="polite" 播报「已更新 N 条建议」;已发送态不只靠颜色(加 ✓ 徽标与禁用属性);截断文本挂 title 或 aria-label 全文;流式期间牌面不动,别让读屏在逐 token 刷新里迷路;prefers-reduced-motion 不涉及(无入场动画,demo 也不加)。

浏览器支持

demo 用到的基础设施:横向滚动区为原生 overflow-x(含 scrollbar-width: thin);按钮禁用态与 focus-visible 均为原生;无自定义滚动条样式依赖。无新依赖。

兼容回退

横向滚动不可用时(键盘用户)建议仍可 Tab 逐个聚焦——滚动区只是容器增强;JS 订阅失效时 chips 仍以静态默认参数渲染;截断失效时显示全文(信息不减)。

来源 4

起源官方零件是 AI Elements Suggestion:容器 Suggestions = 横向 ScrollArea(可拖动滚动条),单体 Suggestion = variant outline + size sm 的按钮,onClick 回调直接吐出 suggestion 字符串、业务侧接 sendMessage——「点击即发送」是该组件的官方用法(无填充输入框中间态);assistant-ui SuggestionAdapter 官方提供 key(run 结束后为该 key 重新生成建议)与 generate(支持流式异步生成)——建议再生成天然防抖到轮次边界。数量上限与防抖更新官方均未规定(未证实);相邻官方机制是 AI SDK 状态机:流式期间建议列表不应逐 token 刷新,应等 status === 'ready'(调研 15§4)。
