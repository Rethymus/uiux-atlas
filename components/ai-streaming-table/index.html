AI 流式表格 AI Streaming Table

流式表格 · Streaming Table · GFM 表格流 · 渐进表格

表格随 token 流生长:块级 memo 的行级结果、fixed 骨架锁列宽、表内滚动不撑破会话锁底——宽表也能流,版面不跳。

结构与 DOM

流式表格是「会生长的块」:表头(先渲染、锁列宽)→ 数据行(随流 append、行级淡入)→ 骨架行(数据未到的占位)。表格整体是 markdown 块,行是它的子结构。

<div class="tbl-scroll" tabindex="0">      <!-- 表内滚动:不撑破会话锁底 -->
  <table style="table-layout: fixed">      <!-- fixed 骨架锁宽 -->
    <caption class="sr-only">季度指标对比</caption>
    <thead><tr><th>指标</th><th>Q3</th></tr></thead>  <!-- 先渲染锁宽 -->
    <tbody>
      <tr>已到数据行(块级 memo,不再重渲)</tr>
      <tr class="skeleton" aria-hidden="true"><td>▒▒▒</td></tr> <!-- shimmer 占位 -->
    </tbody>
  </table>
</div>

关键点:

  • 表格是块、行是子结构——Streamdown/remark-gfm 原生支持 GFM 表格,表格作为块参与块级记忆化:流式时已完成的行块不重渲染(官方 memoization 文档只谈块粒度,行级渐进渲染未单独规范,属块级机制的自然结果);
  • 表头先渲染锁宽——fixed 布局的列宽声明挂在表头,数据未到列宽已定,行数增长不跳;
  • 未闭合表格的 remend 补全未在 termination 文档列出(未证实其专门处理)——流中半截表格可能停在任意行,渲染层要按「表头已定 + 行按需补」策略自稳;
  • 与 AI 流式响应 的分工:正文块交给流式渲染器,表格块交给本条目;与 表格 的关系:交互表格的一等能力(排序/密度/固定列)属于完成态,流式期只做「生长 + 稳定」两件事。

样式与参数

六个参数对应三类声明:布局(fixed/auto)、生长(骨架行数 + 行淡入)、容器(表内滚动 + 收尾策略 + 占位格):

/* fixed 骨架:列宽挂在表头,行数增长列宽不跳 */
.stream-tbl { table-layout: fixed; width: 100%; border-collapse: collapse; }
.stream-tbl th:first-child { width: 38%; }  /* 列宽声明挂在表头 */
.stream-tbl th, .stream-tbl td {
  border-bottom: 1px solid var(--border);
  padding: 6px 10px;
  font-size: 12.5px;
  text-align: left;
}
.stream-tbl td.num { text-align: right; font-variant-numeric: tabular-nums; }
/* 表内滚动:行数超阈值切 overflow,长表不撑破会话锁底 */
.tbl-scroll {
  max-height: var(--stm-max-h, 260px);
  overflow: auto;
  scrollbar-width: thin;
}
.stream-tbl thead th { position: sticky; top: 0; background: var(--bg-elev); }
/* 行级淡入:每行到达依次可见(时长走 CSS 变量) */
.stream-tbl tbody tr { animation: stm-row var(--stm-row-ms, 250ms) ease both; }
@keyframes stm-row { from { opacity: 0; } to { opacity: 1; } }
/* 骨架格:shimmer 扫光占位(与真实行同高) */
.stm-skel td {
  background: linear-gradient(90deg, transparent 30%, color-mix(in srgb, var(--text-1) 8%, transparent) 50%, transparent 70%);
  background-size: 200% 100%;
  animation: stm-sweep 1.4s linear infinite;
}
@keyframes stm-sweep { from { background-position: 100% 0; } to { background-position: -100% 0; } }

数值出处(官方一手 + 未证实如实标注,调研 15§5):

  • 块级 memo:官方记载的 memo 粒度是块(streamdown.ai/docs/memoization),行级渐进是自然结果,未单独规范;
  • 行级淡入/骨架行数/未证实——实现建议,业界通行做法(本站默认 250ms/3 行);
  • Mermaid 同思路:assistant-ui 官方 skill「流中显示 skeleton、完成后才解析」——骨架表迁移的官方相邻依据;
  • sticky 表头/表内滚动:原生 CSS 能力,数值为本站建议档。

动效与交互

  • 生长顺序:表头即时直出 → 骨架行占位(skeletonRows 行)→ 数据行逐行到达、前一行骨架被替换、淡入(rowRevealMs)→ 流结束剩余骨架退场;
  • 列宽稳定:tableLayout: fixed-skeleton 档全程 fixed;autoLayoutOnComplete: on 在流结束切 auto 精修一次(table-layout 本身不可动画,重排钉在流结束这一刻发生——调研建议的 transition 防跳动在列宽层才可能生效);
  • 表内滚动:行数超出 maxBodyHeight 后表体 overflow-auto,外层会话锁底不被抢滚动权;sticky 表头保证纵向滚动时列头可见;
  • 占位格:未完成列用 shimmer 骨架格或「—」占位符(quiet 档),与真实行同高——完成换载零位移;
  • prefers-reduced-motion:停行淡入与扫光,行直出、骨架静态(demo 实现)。

真实产品案例

  • Streamdown memoization 官方文档:块级记忆化让流式 markdown 已完成块不重渲——表格作为块同样受益,GFM 表格由 remark-gfm 原生支持(官方文档,调研 15§5.1);
  • Streamdown termination 文档:termination 清单未列出表格条目——未闭合表格的补全属未证实区域,实现要自行兜底(官方文档缺席即如实申报,调研 15§5.1);
  • assistant-ui Mermaid skill:官方 skill 写明流中显示 skeleton、完成后才解析——「骨架表→真实表」的同构迁移依据(调研 15§5.1);
  • 本站 表格 条目:Ant Table 三档密度、sticky 表头、virtual 虚拟滚动等一等能力,是流式表格「完成态」的去处。

参数敏感度

参数调大会…调小会…
tableLayoutauto 档每行触发列宽重排,整表横跳(仅收尾可用)fixed 骨架是流式默认,列宽恒定代价是长文本列需预设宽度
skeletonRows>5 骨架墙比数据还高,「正在生成」变「空表」1 行骨架指示过弱,长间隔的流会露出表尾;3 行 ≈ 一屏余量
rowRevealMs>500ms 行到达有延迟感,生长节奏被拖慢0 直出最诚实,但批量到达时生长感尽失;250ms 是「看得见生长」下限档
maxBodyHeight>360px 长表抢会话视口,锁底被挤<180px 表内滚动过频,滚动条闪现;260px ≈ 五行视距
autoLayoutOnCompleteon 收尾重排让列宽更贴内容,但要配过渡off 全程 fixed 最稳;内容宽差异大时收尾精修值得开
emptyCellPlaceholderdash 最安静,适合密集数据表shimmer 表达「数据在路上」,回答型表格更合适

经验区间:fixed 全程、骨架 3 行同高、行淡入 250ms、表内滚动 260px;完成态的交互表格能力(排序/密度)不属于流式期。

适用场景 3
  • 回答中流式输出的对比表/数据表——LLM 长回答里最常见的结构化块(GFM 表格原生支持)
  • 行数不可预期的生成式报表——行随流 append,列宽靠 fixed 骨架锁住
  • 嵌入会话锁底视口的宽表——表内独立滚动,不与外层锁底抢滚动权
何时不要用 4
  • auto 布局直排流式表——每行到达都触发列宽重排,整表横跳(fixed 骨架是默认档的原因)
  • 让长表撑破会话锁底视口——行数超阈值必须切表内滚动,否则流式生长把回答推出视口
  • 整表每行重渲(丢块级 memo)——Streamdown 以块为 memo 粒度,已完成行块不重渲染是免费收益,别丢
  • 把骨架行高做得与真实行不一致——完成换载时零位移是底线,行高不一致就是跳版
无障碍

表格用真 <table> 语义(th/scope/ caption),流式期间挂 aria-busy,状态行 aria-live="polite" 播报「已到 N/M 行」;骨架行 aria-hidden(读屏不读装饰占位),数据行到达才进无障碍树;表内滚动区可键盘滚动(tabIndex=0 + 方向键),sticky 表头保证横向滚动时列头不丢;数字列右对齐 + tabular-nums(与站内表格条目同规);prefers-reduced-motion 停行淡入,直出。

浏览器支持

demo 用到的基础设施:table-layout 与 overflow-auto 为原生能力;行淡入为 CSS 动画;sticky 表头(position: sticky)Baseline 全兼容。无新依赖。

兼容回退

CSS 动画不可用时行直出(无淡入,信息不减);shimmer 骨架不可用时占位格退化为「—」或空格;表内滚动失效时表格自然撑开页面(退化为普通长表),锁底由会话层兜底。

来源 4

起源可核验事实:GFM 表格由 Streamdown/remark-gfm 原生支持,表格作为 markdown 块参与块级记忆化——流式时已完成的行块不重渲染(官方 memoization 文档只谈块粒度,行级渐进渲染未单独规范,属块级机制的自然结果);未闭合表格的 remend 补全未在 termination 文档列出(未证实其专门处理);assistant-ui 的 Mermaid 模式「流中显示 skeleton、完成后才解析」同思路迁移到表格:流中骨架表、完成后切换真实数据。列宽稳定与加载态无官方规范——未证实,落地为业界通行做法(fixed 布局 + 表头先锁宽 + 行级淡入 + 表内滚动)(调研 15§5)。
